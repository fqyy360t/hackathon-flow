# hackathon-flow

> **一场黑客松不是一次开发，是一次有截止时间的说服。**
> 这套流程把"说服"拆成可验收的动作：赛前算出评委怎么给分，提交前 7 小时冻结系统，现场只接不造，最后用一个能跑的 demo 加一份经得起追问的记录收口。

**它不是课程，是可执行的文件骨架。** 18 份详规（4,870 行）+ 41 个可直接复制的模板 + 1 套装得上的 git 钩子，装进任意项目目录就能开工。

## 一、它解决什么：三个具体的失败模式

不是"帮你规划比赛"，是三个我实际见过、并且能对应到具体动作的坑。

**① 资料散在群聊和本地文件夹，到现场才发现找不回来。**
一场比赛下来，微信群几千条消息、飞书文档几万字、本地几个文件夹。真正开工时，团队五个人读到的是三个版本，而且最关键的"为什么当初否掉了方案 B"谁也说不清。
→ 对策：**容器在第 1 天建**（不是选完赛道才建），所有产物当场归位。见 [`references/09`](references/09-工程管理.md) §零 的"目录生长表"。

**② 时间轴照抄别人的 42 天赛程，用在一场只有 7 天的比赛上。**
42 天赛程里"决定打不打"占八天。换成一周的线上赛，这八天根本不存在，整张日程表会从第一个节点一路错到底。
→ 对策：**先算 P（纯准备期天数），再选档**。`P = 距提交截止天数 − 比赛时长÷24`，六档骨架（L/M/S/X/T/Z）。见 [`references/00`](references/00-时间轴与门禁.md) §零。

**③ 评分表到手太晚，前面三天的工作白做一半。**
评分表可能赛前给、可能只有维度名、可能路演前才发、可能始终不给。多数队伍拿到后要重写叙事。
→ 对策：**内容与评分项解耦**。先建"内容单元 → 服务哪个评分项"的映射表，评分表一到，30 分钟重排，不重写。见 [`references/12-评分表迟到.md`](references/12-评分表迟到.md)。

## 二、怎么装

两种用法，互不冲突。

**A. 作为 Agent Skill**（Claude Code / Codex / 任何支持 `skills/` 目录的工具）

```bash
git clone https://github.com/fqyy360t/hackathon-flow.git ~/.claude/skills/hackathon-flow-lemon
# 或 codex 对应的 skills 目录
```

目录名建议保持 `hackathon-flow-lemon`（与 `SKILL.md` 的 `name` 字段一致，部分工具会校验）。

**B. 只用模板，不装 skill**

直接复制 `assets/` 到你的比赛项目：

```bash
cp -r assets/flow assets/docs assets/materials 你的项目/
cp -r assets/.githooks assets/scripts 你的项目/ && sh scripts/install-hooks.sh
```

`.githooks/pre-push` 会拦住直推 `main`，紧急通道是 `ALLOW_MAIN_PUSH=1 git push origin main`。

> **Windows 注意**：仓库根有 `.gitattributes` 强制脚本 LF。如果你的项目没有，`pre-push` 被 checkout 成 CRLF 会让 sh 报 `\r: command not found`，约束静默失效。

## 三、首次使用：30 分钟

拿到一条比赛链接（或一张截图、一段群聊）之后：

```
0–5 min    抽三个日期 + 拉赛道总表          → docs/product/赛程卡.md（草案，允许 ⬜未知）
5–10 min   判主办方动机五型（A–E）         → docs/product/赛道盘点.md 第一行
10–20 min  git init + 铺 flow/ docs/ 空壳  → 第一条 commit
20–30 min  列七个必问（问主办方 / 问队友）  → 待问清单
```

结束时的产物**不是"完整目录结构"**，是"资料能落的那几层"：一个能 clone 的空仓库、一份填了三个日期的赛程卡、一份只写了一行结论的赛道盘点。

**判断标准只有一条**：这个目录今天有没有东西要放进去。
`docs/product/证据表.md` 今天就要放差评原文 → 建。`android/` 今天不知道会不会做 App → 不建。

## 四、它凭什么这么判断

三条来源，都能追溯：

| 来源 | 拿到什么 |
|---|---|
| 冠军团队的公开返厂复盘（直播文字稿 6 人 × 数小时） | 赛前判断环的动作顺序、评分逆向的具体手法 |
| 两个冠军仓库的**源码级 + 提交史还原** | Agent 架构的六机制、README 的迭代过程（哪段是赛中写的、哪段是赛后补的） |
| 一场 42 天赛程的群聊全程（6,570 条）+ 官方评分原文 | 真实时刻表、F 点校准（提交 − 7h）、九处数值修正 |

**诚实说明**：这套框架的样本**几乎全是赢家**，没有输家样本。所以它对"怎么赢"的解释力强于对"为什么会输"的解释力——后者目前只能靠反模式清单间接覆盖（67 条里有 30 多条来自失败观察，但没有一场完整的失败复盘）。

## 五、核心判据速览

给 30 秒抓密度用。

| 判据 | 内容 |
|---|---|
| **四道门** | G1 选题门（收敛到 1 个题）→ G2 契约门（范围 + 接口冻结）→ G3 功能冻结门 → G4 交付门（链接全部无痕窗口点过） |
| **一条条件门** | G3.5 换叙事门：评分表若在赛中才给，G3 之后允许一次叙事重排，但**不许改产品** |
| **两个冻结点** | 系统冻结 = **提交 − 7h**；材料冻结 = **提交 − 3.5h**。混在一起，就会在最后两小时既改代码又改 PPT |
| **状态六分类** | `未见实现` / `代码已有` / `局部实测` / `报告待验证` / `完整验收` / `方向待定`。**禁止写"已完成"** |
| **置信度四级** | ✅实证 / 🟡强推测 / 🟠弱推测 / ⬜未知。任何"我猜"必须标级 |
| **重对齐成本** | 准备期 1x → 准备期末段 3x → 开赛前 3 天 6x → 现场 10x → F 点后只改台词 |
| **人数公式** | 人数上限 = 演示链路里**能完全独立的环节数 + 1**。不是"主办方说 5 人就要凑 5 人" |
| **多赛道判据** | 不看加权总分，看**有没有一个赛道出现"三项 ≥ 4"** |

## 六、已知边界

**这五条都会让框架失效，用之前先看。**

1. **只覆盖"有截止时间的竞赛型项目"。** 日常产品开发用它，`flow/` 会变成负担。
2. **不做业务内容。** 它管流程和判据，不管你的行业知识、市场数据、技术选型。
3. **评分表何时到手不由你决定。** 五种到达形态各有打法，但"始终不给"时只能靠往届作品反推，这套判断本身有错的可能。
4. **短赛制（P ≤ 2 天）里，一半的判据会退化成"直觉 + 两条硬动作"。** 时间不够，方法论救不了判断力。
5. **没有输家样本。** 见上一节。

## 谁适合用

- 要打一场黑客松，且**真的想拿名次**（不是为了体验）
- 手上有 3–5 人小队，或愿意一个人当三个人用
- 能接受"赛前花两小时做判断，可能比多写两小时代码更值"

**不适合**：把比赛当成一次学习活动、不追求名次的人。这套东西的每个判据都是为了赢，用在不追求赢的场合会显得很累。
