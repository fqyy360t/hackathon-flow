# 16 · 赛后复盘与资产化

> **48 小时内做完，超时就再也不会做了。** 这不是自律问题：赛后第 3 天开始，记忆会自动美化，你会记成"我们本来就要这么做"。
> 这一节解决一件事：**把一场比赛的投入，变成下一场的起跑线。**

---

## 零、先定一件事：这场赢了还是没赢

**两种复盘的归因方式完全不同，混在一起写就会变成自我安慰。**

| | 赢了 | 没赢 |
|---|---|---|
| 最容易犯的错 | 把运气解释成能力（"我们的叙事打动了评委"） | 把失败解释成环境（"评委不懂技术""赛道太卷"） |
| 复盘必须回答 | **哪一个判断是可以复用的？** 其余的当运气处理 | **哪一步如果换掉，结果会不一样？** 只找一处，不要找十处 |
| 最有价值的产物 | 一套可搬的流程 | **一份能避坑的清单**（比赢家的经验更稀有） |

> **本 skill 现有的样本几乎全是赢家**（同一赛事的两支冠军队 + 官方材料），**没有输家样本**。所以你输掉的那一场，产出物比赢的那场更值钱——它补的是这套框架最大的空白。别浪费它。

---

## 一、四层，从上到下写

**顺序不能反。** 先写事实，再写归因；先归因，再谈复用。反过来会先有结论再找证据。

| 层 | 回答什么 | 载体 | 耗时 |
|---|---|---|---|
| **1 事实** | 几点做了什么，花了多久，拿到什么数 | `docs/reviews/复盘.md` §一 | 20 min |
| **2 归因** | 哪个判断错了 / 哪个执行掉了 | §二 | 30 min |
| **3 可复用** | 哪些能直接搬到下一场 | §三 + 归档到 `assets/` | 20 min |
| **4 反哺** | 改本 skill 的哪个文件 | 直接改 `references/` | 30 min |

---

## 二、事实层：只写数字和时间，不写评价

**规矩：这一层禁止出现"顺利""比较慢""效果不错"。只有时刻、耗时、数量。**

```markdown
## 一、事实

### 时间线（实际，不是计划）
| 时刻 | 事件 | 备注 |
|---|---|---|
| D-42 | 看到比赛链接，当天建容器 | 比上一场早 1 天 |
| D-30 | 报名成功 | |
| D-18 | 定题（推翻第一版） | 第一版被否的原因见 §二 |
| D-8  | 预赛文档提交 | 实际耗时 2.5 天（计划 3 天） |
| O+0 | 开赛，第一次 commit | |
| O+6.5 | 首次部署成功 | **超时 1.5h**（计划 5h） |
| O+14 | 主链路跑通 | |
| O+17（F 点） | 功能冻结 | 与计划一致 |
| O+18.5 | 视频拍完 | |
| O+23 | 提交 | 提前 1h |

### 数字
| 项 | 数 |
|---|---|
| 队员数 / 实际上场 | 4 / 3（1 人当天请假） |
| commit 数 / 涉及文件 | 87 / 214 |
| 预赛文档字数 | 8,400（模板建议 6,000） |
| 路演实际时长 | 被砍到 3 分钟（原准备 5 分钟） |
| 评分表到达时刻 | 未给（形态 E） |
| 重对齐耗时 | 1.2h |

### 结果
| 项 | 结果 |
|---|---|
| 名次 / 奖项 | 第 2 / 无单项奖 |
| 各评分项得分（如公布） | 技术 8/10、商业 5/10、完成度 9/10 |
| 评委现场提问 | 3 问，其中 2 问关于"数据从哪来" |
```

**为什么要这么死板**：三天后你只会记得"当时挺赶的"。而"部署超时 1.5h"这种数才是下次排期的输入。

**评分项得分一定要抄下来**，哪怕只公布总分。**这是你唯一能拿到的、带权重的真实反馈。** 拿不到就记"未公布"，不要猜。

---

## 三、归因层：分清「判断错」和「执行差」

**这两类的修法完全不同，混着写就修不了：**

| 类型 | 定义 | 修法 | 例子 |
|---|---|---|---|
| **判断错** | 选了错的方向，做得再好也没用 | 改**判据**（在 skill 里加一条 rule） | 选了商业权重高的赛道，但我们没有商业的人 |
| **执行差** | 方向对，但没做到 | 改**排期 / 分工 / 工具** | 部署计划 5h，实际 6.5h |

**每场只许写 3 条，且必须写成"如果重来一次，我在哪一刻改什么"。**

```markdown
## 二、归因（每条必须有"换掉哪一步"）

### 判断错 1：把"技术上最酷"当成"最容易被选中"
- **证据**：预赛文档里技术部分 60%，商业部分 15 页里的 2 页；评委 3 问里 2 问数据来源
- **当时为什么这么判**：赛题描述里技术词多，误判成技术型赛
- **如果重来**：在看到赛题当天就去查往届获奖项目的**共同点**（不是技术栈），这一步 1 小时
- **归到哪**：`13` §二 已有的五型判据里，"往届获奖者后来怎么了"这条我**没真的去查**

### 执行差 1：首次部署估 5h，实际 6.5h
- **卡在哪**：域名解析等了 40 分钟 + iOS 证书 55 分钟，两件都是**等待型**任务，本该与别人并行
- **根因**：排期时把"等待"当成了"工作"，没标在时间轴上给第二个人
- **如果重来**：开赛第 1 小时就把等待型任务（域名 / 证书 / 审核）全部发出去，然后不管它
- **归到哪**：`00` §七 时间分块加一条"等待型任务先发后做"

### 没搞清的一件事（不硬解释）
- 评委说"完成度高但没看到差异化"，我们至今不知道这个赛的"差异化"具体指什么
- **处理**：登记为 `flow/assumptions.md` 的 ⬜未知，下次同类赛第一件事是问主办方
```

**最后一栏"没搞清的一件事"必须有。** 一场比赛里一定有你想不通的地方，硬给一个解释等于把错误结论写进 skill。

---

## 四、可复用层：三档，只有第一档值得归档

**别把整仓代码当资产归档。** 下一场复用不了整个项目，只能复用零件。

| 档 | 判据 | 处理 |
|---|---|---|
| **A 直接可用** | 下一场**不改或改 <10%** 就能用 | 抽出来放 `assets/materials/` 或独立小仓库，**写清"怎么用"三行** |
| **B 改 30% 可用** | 骨架对，内容换 | 只记**位置 + 一句话为什么值得留**，不搬（搬了会变成死文件） |
| **C 一次性** | 只对这场比赛成立 | 不归档，不要有感情 |

### 通常落在 A 档的东西（按复用率排序）

| 资产 | 为什么能复用 |
|---|---|
| 部署脚本 / `docker-compose.yml` / CI 配置 | 换项目只改镜像名和端口 |
| 登录 / 鉴权 / 支付的最小实现 | 每场都要，每场都重写，最浪费 |
| 路演 HTML 骨架 + 讲稿结构 | `06` §七 那套，换个产品名就能用 |
| 提交页 HTML + 机械检查脚本 | 结构不变，内容换 |
| 证据表 / 评分映射表的**表格结构** | 空表本身就省 30 分钟 |
| 一份"能跑的最小 Agent 脚手架" | 有 Agent 赛就用得上 |

### 通常落在 C 档的东西（别归档）

业务逻辑、页面组件、这次的数据集、模型权重（除非可公开）、为这场比赛起的产品名和视觉。

**判据一句话**：**下一场开赛时，我会不会主动去找这个文件？** 不会就不归档。

---

## 五、反哺层：直接改 skill，不写"下次注意"

**"下次注意"是复盘里最没用的一句话**——它既没有触发条件，也没有具体动作。

把它改成本 skill 里的一条可执行规则：

| 复盘的发现 | 改哪个文件 | 改成什么形态 |
|---|---|---|
| 某个判据判断错了 | `13` / `08`（判据类） | 改判据表的一行，或在反模式里加一条 |
| 某一步耗时被低估 | `00` §七 / §九 校准表 | 填"实际耗时"一列 |
| 某个交付物反复漏 | `06` §九 / `materials/交稿前机械检查.md` | 加一条检查项 |
| 某个工具/命令踩坑 | `references/` 对应文件 + `flow/踩坑记录.md` | 写清"症状 + 根因 + 绕法" |
| 评分表形态又是一种新的 | `12` | 加一个形态（F 型） |
| 赛制规则本身特殊 | `11-真实赛程校准.md` | 加一节，标清"这是第几场样本" |

### 反哺的三条纪律

1. **一条发现只改一处。** 同一件事写进三个文件，下次改的时候会漏两个。
2. **标注样本量。** 写"这场是这样"，不写"通常是这样"。**一场样本得出的是假设，不是规律。**
3. **改完在本文件 §六 记一行**，否则过一个月你不知道哪些改动是实测来的、哪些是推的。

---

## 六、复盘帖（对外）：写给下一届，不写给自己

**主办方最爱看这个，且它能带来下一次的邀请 / 内推 / 合作。** 但它和内部复盘是两份东西。

| | 内部 `docs/reviews/复盘.md` | 对外复盘帖 |
|---|---|---|
| 读者 | 你和队友 | 下一届参赛者、主办方 |
| 写不写失败 | 全力写 | **写，但只写能帮到别人的** |
| 写不写内部矛盾 | 写 | 不写 |
| 写不写具体分数 | 写 | 通常不写（除非主办方公开） |
| 长度 | 不限 | 1,500–2,500 字 |

### 对外帖的六段（可直接抄）

```markdown
## 1. 我们做了什么（100 字 + 1 张图）
一句话 + 一张最终界面。不要从"随着 AI 技术的发展"开头。

## 2. 我们怎么定题的（300 字）
写出**被否掉的两个方向 + 否决理由**。这是最有价值的一段——
别人能抄的不是你的答案，是你否掉答案的方式。

## 3. 现场 48 小时怎么排（300 字 + 时间表）
真实的时刻表，包括卡住的地方。不要写成"高效协作、紧密配合"。

## 4. 我们踩的三个坑（500 字）
每个坑写：症状 → 我们以为的原因 → 真正的原因 → 怎么绕。
（例：视频链接 54 分钟后过期 / 私有仓库评委打不开 / 内网地址写进配置）

## 5. 如果重来一次（300 字）
只写三件，按收益排序。

## 6. 感谢 + 联系方式（100 字）
```

**不要写的东西**：感谢主办方三段、团队每个人的赞美、"这次比赛让我学到了很多"。

## 七、仓库赛后怎么处理

| 动作 | 什么时候 | 注意 |
|---|---|---|
| 清密钥 / 内网地址 / 客户数据 | **赛后 48h 内，一次做完** | 这次可以改历史甚至换仓库（已经交完链接了，但**如果链接还会被评委回看，先备份再换**） |
| 补 `README` 的"赛后状态"一行 | 赛后 48h | 例：`本仓库为 XX 黑客松参赛版本，演示环境已下线，本地按 README 可运行` |
| **README 升级成"可被追问的版本"** | 赛后 48h，约 2h | 四步见 `17` §六：口径对照块（"当时说过的 vs 现在代码里的"）/ 复盘链接 / 常见问题 / 按动机换结尾。**这一招赛中写等于自曝，赛后写是最强的信任武器** |
| 私有 → 公开 | 确认规则允许后 | 公开后能当作品集；**先确认参赛协议有没有保密条款** |
| 打 `v1.0` tag 保留 | 已做（`15` §六） | 别再改动这个 tag |
| 目录搬家 / 重构 | 赛后，**单独一个 commit** | 赛时禁止（`15` §八），赛后可以，但要留 tag 对照 |

---

## 八、复盘模板怎么填（`assets/docs/复盘.md`）

模板已经按上面四层排好。三个填写要点：

1. **§一 时间线必须用真实时刻**，从聊天记录 / `git log` / 提交截图里抄，不靠回忆
   ```bash
   git log --format="%ad %s" --date=format:"%m-%d %H:%M" --reverse | head -40
   ```
2. **§二 归因写满 3 条就停**，第 4 条开始都是重复或情绪
3. **§五 反哺改完立刻提交**，commit message 写 `docs: 反哺第 N 场（XX 赛）`

---

## 九、和 `00` §九 的关系

`00-时间轴与门禁.md` §九 是**动作表 + 排期校准表**（什么时候做什么、计划 vs 实际耗时）。
这一份是**内容怎么写**（四层结构、归因分法、复盘帖）。

两份都要用：先按 `00` §九 把动作走完，再按这份把内容填进去。

**最后一句判据（沿用）：这次复盘能不能让下一场的准备期少花两天？不能就白沉了。**
