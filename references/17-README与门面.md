# 17 · README 与门面：新来的人怎么 30 秒知道这是什么

> **这是"门面"，不是"文档"。** 一个陌生人打开仓库，前 12 行决定他往不往下看。
> 它与 `15` 的项目结构文档是**两个读者**：README 给"要不要继续看"，结构文档给"这工程是不是真的"。
> 本篇的判断基于一份实测样本（`OntoCare`，智能服务赛道冠军仓库）的**提交历史还原**，不是凭观感。

---

## 零、先看一份"看着清晰"的 README 是怎么长出来的

大多数人以为是"边做边写，最后自然成型"。实测结论**完全相反**。

### 实测时间线（18 个 commit / 4 个时间簇 / 跨 8 天）

| 北京时间 | 这一簇做了什么 | commit 数 |
|---|---|---|
| **10-19 04:27 → 04:59**（32 分钟） | **首次发布整仓**：源码 + `docs/` + `presentation/` + HTML 图文介绍 + 开 Pages + 架构/用法/证据文档 | **9** |
| **10-19 14:29 → 15:28**（约 1 小时） | 补演示视频与"七层视角"、修 Release 视频链接、加视频播放页、换成真实部署截图 | 6 |
| **10-22 01:29 → 02:25** | 加获奖证书、**清洗公开版材料并对齐评测口径**、同步内嵌 Markdown | 3 |
| **10-26 18:17** | 加一个"项目 / 演示 / 复盘"共享链接页 | 1 |

### 三个可以当结论的观察

**① 它是赛后写的，不是赛中。**

三条硬证据，不靠猜：

- root commit 就是 `Publish OntoCare source, documentation and readable HTML introduction`——**整仓一次性发布**，说明比赛期间没有一个持续 push 的仓库
- 里面有"赛后复盘""获奖证书原图""AI 产品实习意向"——这三样赛前赛中都不可能存在
- README 写着"演讲中提及的这些机制保留为历史方案表述，**不作为已实现能力**"——只有赛后敢这么自我否认

**② 但素材是赛中攒的。**

root commit 一上来就带了 `docs/`（图文介绍 + 演讲稿原文）、`presentation/`（路演 HTML/PDF/PPT）、`OntoCare/docs/`（架构 / 使用 / Prompt / 验收）三套体系。**32 分钟推不出这些**——它们是赛中就写在飞书/wiki 里的，赛后只是搬进 git 并重排。

**③ 第一波只有 32 分钟，说明"排版"根本不花时间。**

9 个 commit 全在半小时内，且 message 全是 `Publish` / `Document` / `Expand` / `Feature`——这是**把已有材料分批落位**的动作，不是"写"。真正花时间的是赛前攒素材，和赛后 8 天里的口径清洗。

### 由此得到的分工，这条最重要

| 阶段 | 该做什么 | 不该做什么 |
|---|---|---|
| **赛中** | 攒素材：架构图、功能清单、评测原始结果、**每次"没做完"的记录**、截图 | 别指望赛中把 README 打磨成型——你没有余量 |
| **F 点前 2h** | 只写三段：**第一屏 / 怎么跑 / 已知边界** | 别写"选型理由"和"设计取舍"，那时候写必然失真 |
| **赛后 48h 内** | 组装：口径表、复盘链接、按动机调整结尾 | 别拖过一周，细节忘光了只能现编（现编一被追问就露） |

> **反面教材（同一份样本）**：它的「快速开始」和「常见问题」是**赛后补的**——10-19 第 3 条 commit 才补文档，第 2 天才补视频。而这两段恰恰是评委最需要、也最能证明"真能跑"的。
> **你比赛后有这个仓库，但你没有它的 8 天。** 所以这两段必须在 F 点前就写完。

## 一、它"看着清晰"的五个手法，全部可抄

排版不是原因。清晰来自这五件事，每一件都能单独拿去用。

### 手法 1：第一屏是分流器，不是目录

它 README 的第一屏长这样（结构，不是原文）：

```
# <产品名>
## 点击打开：图文交互项目介绍 ↗        ← 一个巨大的链接
   [预览图，整屏宽]
   建议先看这一页：架构、双端截图、六步流程、闭环
---
**<一句话定位>**
<两行：把散落的求助串成什么链路>
联系我们 · 赛后复盘 · 完整开发过程 · 讲解稿 · 技术架构 · 快速开始
```

**关键动作：把"深度"外包给一个 HTML 页。** README 自己不承担"讲清楚"的责任，只承担"把他送过去"的责任。

这解决了你担心的那个问题——**"新来一个人不知道这玩意儿咋回事"**。解法不是把 README 写长，是给它一个**第一跳**。所有细节在图文页里，README 永远只有一屏。

> 成本：一个 HTML 页（`06` §3.1 的提交页可以复用）+ 一张预览图。**你的决赛提交页本来就有，赛后再挂到 Pages 上就行。**

### 手法 2：「从哪里开始阅读」——按目的分四路

这是整份 README 里最值得抄的一个表，四行：

| 你的目的 | 建议路线 |
|---|---|
| 快速理解这个项目 | 架构图 → 核心功能 → 三个核心设计 → 评测结果 |
| 看比赛过程与体会 | 赛后复盘 → 当时的演讲稿 |
| 把代码在本机跑起来 | 快速开始 → 模型配置 → 本地页面 → 常见问题 |
| 审阅技术实现 | 架构 → 源码职责 → API 入口 → 测试与原始记录 |
| 继续开发 | 关键 Bad Case → 数据与知识维护 → 贡献方式 |

**为什么它有效**：评委、HR、开源路人、你三个月后的自己，这四种人想要的完全相反。一个统一的线性章节顺序必然得罪其中三个。**分流表让每个人只读他那一路，每条路 3–5 跳。**

**反过来看**：绝大多数 README 只有一条路径（把自己写代码的顺序当成了阅读顺序），于是"想快速了解"的人被迫先看"环境要求"。

### 手法 3：数字从不裸奔

它的每个成绩后面都跟着一段口径。原样摘两处：

> **83.8%（62/74）**｜历史在线核心任务首轮硬性断言通过率｜[历史结果]
> **98.6%（73/74）**｜修复后核心任务单轮复测硬性断言通过率｜[修复复测]

不止如此，还专门写了一段防误读：

> 以上是不同版本的历史记录与复测，**不能合并解释为"8 轮问题解决率从 83% 提高到 98%"**。

**这是"可信度 > 大小"的极致用法**。它先给你的数字打个折，然后你反而全信了。`02` 里那条"冠军数字只有 2.42%"是同一个手法。

**写法：`数字 + 分母 + 这一轮的口径 + 来源链接`，四件套不能缺。** 缺任何一个，数字就从资产变成负债。

### 手法 4：「当前实现 vs 历史表述」——赛后最强的信任武器

它反复出现同一句式，至少六处：

| 演讲里说过的 | README 里的处理 |
|---|---|
| 图谱 + 向量混合检索 | "当前主链路未接入 ChromaDB、Redis 或 Embedding 向量召回。'图谱＋向量混合检索'是历史演讲中的方案方向" |
| 双本体 = RDF/SPARQL | "当前实现采用 JSON 数据、实体关联和 Python 规则。**它不是 RDF/SPARQL 图数据库系统**" |
| 独立 Supervisor Agent | "当前**没有**独立 Supervisor Agent、自动向量权重更新或模型参数训练" |
| 自动发布知识 | "自动发布、自动向量降权和独立监督代理属于**后续方向**" |

**这是最反直觉的一招**：主动把"我们吹过的"和"我们做出来的"分开列，看起来像自曝，实际效果是——

> 评委读完的反应不是"你们没做到"，而是"**这个队居然知道自己做到哪**"。

而"知道自己做到哪"恰好是评分表里最难伪装的项。

**但这一招有严格前提：只在赛后用。** 赛中（还在被评分时）写这个等于自己扣分。所以它属于 `16` 的赛后资产化，不属于交付。**赛中要做的是另一件事：把当时说过的原话存下来**（`docs/product/路演.md` 原文不动），否则赛后想对照都没有对照物。

### 手法 5：常见问题 = 别人的失败点清单

它最后有一段 12 行的表，标题就叫「常见问题」，格式是"现象 → 检查顺序"。摘几条：

| 问题 | 检查顺序 |
|---|---|
| 打开 Pages 后不能聊天 | Pages 是静态介绍；按快速开始运行后端 |
| 改了环境变量却还是旧模型 | 检查本机 `demo_api_config.json` 是否覆盖环境变量 |
| 请求 404 或模型不存在 | 检查根地址是否重复追加 `/chat/completions` |
| 上传成功但没有识别结果 | 检查视觉服务是否支持图片输入 |

**每一行都来自一次真实的失败。** 没有一行是"想象中的问题"。

写法判据：**写完"怎么跑"之后，立刻把你刚才踩的坑按顺序记下来。** 你踩过的坑就是别人的第一个坑——而且这是唯一一种"你自己不需要额外花时间"的文档：不写，那些时间就白花了。

## 二、三个绝对不能抄的地方

抄手法，不要抄形态。

| 不能抄 | 为什么 | 你该怎么做 |
|---|---|---|
| **长度**（20+ 章节、6000+ 字） | 它是给 HR / 开源路人 / 后续开发者看的**作品集**，不是给评委的提交物。评委只有 3 分钟 | **正文压到 6 段、每段 ≤ 5 行**，超出的全部移到 `docs/architecture/项目结构.md` |
| **结尾的"联系与实习意向"** | 那是 **A 型（企业招人）** 赛的专属加分项。换一场赛放这个会显得跑错场 | 按 §五 的动机五型换结尾 |
| **五套冗余载体**（MD + HTML + Pages 播放页 + Release + 双语内嵌） | 它花了 8 天反复对齐这几套（`Align embedded downloadable Markdown with cleaned public copy` 就是在修同步问题） | **赛中只留两套**：README（喂评委）+ 提交页 HTML（喂路演）。其余赛后再说 |

> **最贵的教训藏在它自己的 commit message 里**：`Align embedded downloadable Markdown with cleaned public copy` ——同一份内容存了两处，就要反复手工对齐。**赛中任何"同一内容存两份"都会变成提交前两小时的加班。**

## 三、README 分三次写，不是一次

| 时点 | 写哪几段 | 耗时 | 为什么是这个时点 |
|---|---|---|---|
| **G2 后（准备期末段）** | ① 第一屏（名字 / 一句话 / 一个入口）② 怎么跑（三条命令）③ 已知边界 | 40 min | 这三段决定了"别人能不能碰你的项目"，越早写越早发现问题（往往发现命令根本跑不通） |
| **F 点前 2h** | ④ 验证结果（真实输出 + 状态表）⑤ 截图（≥1080p，别截代码） | 30 min | 只能用**冻结后**的输出，早写等于写了个假的 |
| **赛后 48h** | ⑥ 口径表 ⑦ 复盘链接 ⑧ 结尾（按动机） | 60 min | 口径需要对照原始记录；复盘必须趁记忆还在 |

**唯一允许"最后才写"的是第二屏的分流表**——它依赖最终章节结构，5 分钟就能排完。

**绝对不能在 F 点后才写的：③ 已知边界。** 它是赛中唯一"必须当场记"的东西：每砍掉一个功能、每降级一次方案，就在 `flow/踩坑记录.md` 记一行。**不记，赛后你只会记得成功的部分**，而"边界"正是评委分辨真假的那一栏。

## 四、结构：三层分流器（可直接套）

```
┌─ 第一屏（12 行内）──────────────────────┐
│ 名字 + 一句话 + 【一个巨大的入口】+ 一行辅助链接      │  ← 决定"要不要往下"
├─ 第二屏：从哪里开始阅读（4 行表）──────────┤  ← 决定"读哪一路"
├─ 正文六段 ─────────────────────────────┤
│  ① 这是什么问题（3 行 + 1 张对比表）              │
│  ② 功能是什么（分端列，每条一句，不写实现）         │
│  ③ 三个核心设计（每条带"我们没做什么"）           │
│  ④ 怎么跑（三条命令 + 四个入口）                 │
│  ⑤ 验证结果（口径表：数字/分母/范围/来源）        │
│  ⑥ 边界（3–6 条，含"哪里会崩"）                │
├─ 第三屏：仓库结构（≤12 行，每行一句职责）──────┤
└─ 结尾：按动机五型（§五）──────────────────┘
```

**每段篇幅上限（超了就砍，不是删字，是移到结构文档）：**

| 段 | 上限 | 判据 |
|---|---|---|
| 第一屏 | 12 行 | 手机一屏能看到"名字 + 一句话 + 入口" |
| 分流表 | 4 行 | 每个读者一路，超过 5 路说明你没想清读者是谁 |
| ①–⑥ 正文 | 共 60 行 | 每段 ≤ 10 行，表格不算行数 |
| 仓库结构 | 12 行 | 只列**有职责的层**，`15` §二 的标准 |
| 全文 | **≤ 120 行** | 超过就是结构文档，不是 README |

> **120 行是硬线。** 那份样本 6000+ 字是作品集规格；黑客松提交物的合格线是"评委 30 秒能判断、3 分钟能问住"。

## 五、结尾按主办方动机换（接 `13` §二 的五型）

同一份项目，结尾放错东西，观感会从"懂行"变成"跑错场"。

| 型 | 动机 | 结尾放什么 | 千万别放 |
|---|---|---|---|
| **A 企业招人** | 锁定候选人 + 内部点子 | **联系方式 + 求职/合作意向**（样本就是这一型：QQ 邮箱 + 微信 + "备注 GitHub＋来意"） | 市场规模预测 |
| **B 企业生态** | 推广自家 SDK/云/硬件 | "如何基于本赛提供的 X 继续扩展"+ 一行接入代码 | 与它技术栈无关的选型炫耀 |
| **C 投资招商** | 找项目 + 地方落地 | 商业化路径一页 + 团队背景 + 下一步里程碑 | 实习意向、个人简历式自述 |
| **D 社区技术**（Kaggle/天池） | 找方案 | 复现脚本 + 榜单成绩 + 单次运行成本 | PRV、痛点叙事 |
| **E 政府命题** | 采购前方案征集 | 落地场景 + 合规/数据安全说明 | 发散型延展、多条路线 |

> 判错型比内容差更难救：在 A 型赛里讲"千亿市场"，评委是业务线总监，他会觉得你在念 PPT；在 C 型赛里放"欢迎 HR 联系"，VC 会直接翻页。

## 六、赛后升级（可选，收益最高的一段）

赢或没赢都能做，成本约 2 小时，产出一份**能被追问的**仓库。

1. **加口径对照块**（§一 手法 4）：把 `docs/product/路演.md` 的原话逐条对照代码
   - 格式：`当时说过的 → 现在代码里的 → 状态（完整验收 / 局部实测 / 未见实现 / 方向待定）`
   - **没做的就写没做。** 一份主动写"我们没做到这三件"的 README，比一份完美的 README 可信度高一个量级
2. **加复盘链接**：`docs/reviews/复盘.md`（`16` 的四层）→ 一个链接
3. **补常见问题**：把 `flow/踩坑记录.md` 抄成"现象 → 检查顺序"表
4. **换结尾**：按 §五 判定本赛动机再写

> 这一节的四步，恰好就是那份样本 8 天里做的事（除第 1 步它做得更狠：连"历史方案表述"都逐条标出来了）。

## 七、自查（12 项，全过才算合格）

- [ ] 第一屏 12 行内能看到：名字 / 一句话 / **一个能点的入口**
- [ ] 手机打开能一屏看到上面三样
- [ ] 分流表 ≥ 3 路，每路 3–5 跳，且指向的都是真实存在的文件/锚点
- [ ] 「怎么跑」三条命令封顶，且**在新 clone 的空目录里验证过**（`15` §七）
- [ ] 每个数字都有：分母 / 数据范围 / 来源链接，缺一个就不写
- [ ] 状态只用六分类，全文搜不到"已完成"
- [ ] 边界段 ≥ 3 条，其中至少一条是"什么情况下会崩"
- [ ] 仓库结构 ≤ 12 行，每行有职责描述，没有 `package-lock.json` 这类噪声
- [ ] 全文 ≤ 120 行
- [ ] 结尾与主办方动机（A–E）匹配
- [ ] 无 `example` / `your-key` / `TODO` 占位残留
- [ ] **无痕窗口点一遍所有链接**（私有仓库对无权限者返回 404，看起来就是"不存在"）

## 八、这套做法的边界

- **样本只有一份冠军仓库**，且是「A 型企业招人型 + 有充足赛后时间」的形态。**它的清晰度有一半来自"赛后 8 天精修"，赛中没有这个预算。**
- 「当前实现 vs 历史表述」这一招**只在赛后安全**。赛中用等于主动暴露短板；但赛中必须**留存原话**，否则赛后无从对照。
- 120 行上限是按"评委只看 3 分钟"估的。若某赛明确要求 README 兼作技术评审材料（少部分赛会这么要求），上限应放宽到 300 行，并同步在 `docs/product/赛程卡.md` 记一条。
- 分流表的四路读者是从样本 + 通用开源惯例推的。**若评委实际只看提交页不打开仓库**（很多赛如此），README 的投入应降到 1 小时以内，全部预算移到提交页。
