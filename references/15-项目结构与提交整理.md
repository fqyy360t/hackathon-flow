# 15 · 项目结构文档与提交前整理

> 两件事常被混成一件：**写"这个项目是怎么组织的"**（结构文档）和**"把这个仓库收干净再交"**（整理）。
> 它们的时间点差一整场：**结构文档边做边长，整理一次做完。**
> 混在一起的结果是——到提交前两小时才开始写结构文档，而那时"为什么这么选"已经忘了。

---

## 零、先分清三份文档，混了就都不合格

很多队伍只写一份 README，然后把结构说明、验证结果、商业价值全塞进去。结果是评委扫 30 秒什么都没抓到。

| 文档 | 读者 | 读多久 | 读完要做什么决定 | 放哪 |
|---|---|---|---|---|
| **README** | 评委 / 路人 | **30 秒** | "这东西跟我有关吗？要不要往下看" | 仓库根 `README.md` |
| **项目结构文档** | 想跑起来的人 / 评估工程量的人 / 你自己三个月后 | **10 分钟** | "这工程是真的还是壳？我能不能拉起来" | `docs/architecture/项目结构.md` |
| **决赛提交页** | 评委 | **3 分钟** | "给它打多少分" | `materials/index.html`（见 `06` §3.1） |

**三份的写法不能互相替代：**

- README 里贴完整目录树 → 前 30 秒全是 `├──`，评委直接跳过
- 结构文档里写商业价值 → 读的人已经在看代码了，他关心的是"哪个文件负责什么"
- 提交页里写部署步骤 → 评委不会部署，他只看你能不能跑

**README 里只放一行指向**：`工程结构见 [docs/architecture/项目结构.md]`。

> **README 自己不承担"讲清楚"。** 它是三层分流器：第一屏给入口、第二屏按目的分四路、正文六段 ≤120 行。
> 写法、实测依据、12 项自查见 **`17-README与门面.md`**。

---

## 一、项目结构文档：七段

这是"比赛队伍交出来的那种项目结构文档"的标准骨架。**七段都要有，但每段不许超过下面给的篇幅。**

| # | 段 | 写什么 | 篇幅 | 最容易犯的错 |
|---|---|---|---|---|
| 1 | **一句话 + 架构图** | 一句话说清这是什么 + **一张图**（不是三段话） | 1 句 + 1 图 | 用文字描述架构 |
| 2 | **目录树 + 每层职责** | 只列**有职责的层**，每层一句话"这里放什么、不放什么" | 15–30 行 | 把 `tree` 全量贴进去 |
| 3 | **技术栈 + 选型理由** | 每一项写"**没用 X，因为 Y**" | 5–8 条 | 只列名字（"FastAPI、React、Postgres"）没信息量 |
| 4 | **一条主链路** | 从用户动作到数据落库，**标出经过的文件路径** | 1 条链，5–10 步 | 画了五条链路，一条都没标文件 |
| 5 | **关键设计决策** | 3 条，含**被否决的方案 + 原因** | 3 条 | 只写"我们用了分层架构" |
| 6 | **怎么跑 + 怎么验** | 命令 + 验证输出 | ≤ 10 行 | 命令自己没验证过 |
| 7 | **已知边界** | 什么没做、什么没验证、哪里会崩 | 3–6 条 | 假装全做完了 |

> **第 1 段那"一张图"不是装饰。** 评委看结构文档的平均耐心是 10 分钟，图占掉的是他建立整体印象的 2 分钟。没有图，剩下 8 分钟他会用来找你的漏洞。
> 图不用精美：`mermaid` 或手画的 PNG 都行，但**必须能看出"哪块是入口、哪块是逻辑、哪块是外部依赖"**。

## 二、目录树怎么写才不废

**判据：一条目录行如果删掉，读的人会不会对这块产生误解？会，才留。**

### 反例（全量 tree，等于没写）

```
├── .gitignore
├── package.json
├── package-lock.json
├── tsconfig.json
├── vite.config.ts
├── public/
│   ├── favicon.ico
│   └── logo.svg
├── src/
│   ├── main.tsx
│   ├── App.tsx
│   ├── components/
│   │   ├── Button.tsx
│   │   ├── Card.tsx
...
```

读的人从这 40 行里得不到任何判断。他要知道的是**边界在哪**，不是有几个文件。

### 正例（只写有职责的层）

```markdown
web/            前端。只做展示和调 API，不放业务规则
  src/pages/    路由级页面，一个文件对应一个 URL
  src/api/      所有后端调用的唯一出口（改接口只改这里）
api/            后端。所有业务规则在这里
  routes/       HTTP 入口，只做参数校验 + 转发，不写逻辑
  services/     业务逻辑，可单测
  adapters/     外部服务（LLM / 支付 / 硬件），**换供应商只改这一层**
ml/             离线模型：训练脚本 + 权重，**不参与在线推理**
shared/         前后端共享的类型定义，**任何人不得修改**
docs/           见 docs/README.md
```

**三条硬规则：**

1. **每一层必须有一句"不放什么"**——这比"放什么"有用，因为边界靠排除定义
2. **标出"只能从这里改"的单点**（`src/api/`、`adapters/`）——这是评委判断"这工程能不能维护"的最快信号
3. **不列生成物**（`node_modules/`、`dist/`、`.venv/`）——列了显得没做过工程

## 三、主链路那一节：一条链，标文件路径

**只写一条。写五条等于没写。**

格式固定成这个样子，可以直接抄：

```markdown
## 主链路：用户上传一张图 → 看到检测结果

1. `web/src/pages/Upload.tsx` —— 选文件，POST `/api/detect`（FormData）
2. `api/routes/detect.py:14` —— 校验 MIME 与大小（>5MB 返回 413）
3. `api/services/pipeline.py:31` —— 调 `adapters/vision.py`，超时 8s
4. `api/adapters/vision.py:9` —— 第三方模型，失败时降级到本地轻量模型
5. `api/services/score.py:22` —— 阈值 0.62，低于则标 `low_confidence`
6. `shared/schema.py:40` —— 响应结构（前后端共用）
7. `web/src/pages/Result.tsx` —— 渲染，`low_confidence` 显示黄色提示

**为什么只走这一条**：它是 demo 里要演的那条。其他分支没验证，写在下面「已知边界」。
```

**标行号的三个好处**：你自己三个月后能直接跳过去；评委能验证你没编；写的时候会发现自己记不清哪个文件——**记不清就说明那一层你没管住**。

## 四、选型理由：只写被否决的方案

**"我们用了 FastAPI" 这句话的信息量是零。** 任何人都会选一个流行框架。

有信息量的写法是**否决**：

| 写法 | 信息量 |
|---|---|
| ❌ 后端用 FastAPI | 0：证明你装过依赖 |
| ✅ 后端用 FastAPI，**没用 Flask**：Flask 的同步模型在 8s 的模型调用上会阻塞整个 worker，我们只有一个实例 | 有：说明你算过并发 |
| ✅ 数据库用 SQLite，**没用 Postgres**：单机部署、无并发写，省掉运维；代价是不能多实例，写在「已知边界」 | 有：说明你权衡过并承认代价 |
| ❌ 前端用 React | 0 |
| ✅ 前端用 React，**没用 Vue**：队里三人只有 React 是 L2（`08` §三的分级） | 有：说明是人的约束不是技术偏好 |

**规矩：每条选型理由必须带一句代价。** 没有代价的选型 = 没权衡过。

## 五、文档什么时候写：三次生长

**这是这一节最该记住的部分。结构文档不是"最后写"，是"分三次长出来的"。**

| 时点 | 写到什么程度 | 为什么不能晚 |
|---|---|---|
| **A-2 建模块（G1 后）** | 建文件，只写**第 2 段（目录树）和第 3 段（选型）的骨架**——允许全是 `⬜待定` | 目录是那时定的，顺手记 10 分钟；到 S5 再回忆"当时为什么分这五个目录"是想不起来的 |
| **S3（准备期最后 1/3）** | 每做一次**不可逆的技术选择**，在**第 5 段**（关键决策）加一条，带被否决方案 | 决策当场记一句话，成本 1 分钟；三天后要还原理由，成本 20 分钟且大概率失真 |
| **S5 整理（F 点前）** | 补**第 1 段（架构图）、第 4 段（主链路）、第 7 段（已知边界）** | 这三段依赖"最终形态"，只能最后写。但它们加起来只要 40 分钟——**前提是前两段已经在** |

**反直觉点：最后写的那三段，恰好是评委最容易看懂的三段。** 所以很多人到提交前才写它们，写完发现第 2、3、5 段是空的，只能现编——而现编的选型理由，一被追问就露。

## 六、提交前整理：90 分钟，六步，顺序不能反

**该在 F 点前 6 小时做，不是提交前 30 分钟。** 因为第 4 步（新机器验证）一旦失败，要修的东西可能是一小时起步。

| 步 | 动作 | 为什么必须在这个位置 |
|---|---|---|
| **1 清** | 删密钥、删 `.env`、删数据 dump、删 `node_modules/` `.venv/` `dist/`、删空目录、删注释掉的死代码；**读一遍 `git log --oneline`，把 `update`/`111` 这类 message 至少在新 tag 上不再出现** | **先删，因为删完才知道 README 里哪些路径要改。** 反过来先写文档，再删文件，文档全废 |
| **2 正** | 统一命名（文件名 / 环境变量 / 接口字段）、把所有 `example` `TODO` `localhost:3000` 逐个替换或确认 | 这一遍必须**全文搜**，不靠眼睛 |
| **3 补** | README（四段）、项目结构文档（七段）、`LICENSE`、`.env.example`、`.gitignore`、`docs/README.md` 索引 | 补在删之后，路径才是对的 |
| **4 验** | **新机器验证**（见 §七） | 唯一诚实的检查。放在"锁"之前，因为失败还要改 |
| **5 锁** | 打 tag `v1.0`，之后只在这个 tag 上交付；`main` 继续改也不影响评委看到的版本 | 交付链接指向 tag，不指向 `main`（`14` §六） |
| **6 点** | 所有链接在**无痕窗口 + 手机**各点一遍 | 最后一步，因为前面的改动都可能让链接失效 |

### 第 1 步的"清"，具体清什么

| 类型 | 在哪找 | 判据 |
|---|---|---|
| **密钥** | `git log -p --all -S "sk-"`、`git log -p --all -S "AKIA"`、全部 `.env*` | 只要进过历史，**就当作已泄露**，去后台吊销重发 |
| **本地路径** | 搜 `C:\Users`、`/Users/`、`127.0.0.1:8` | 出现在代码或文档里 = 换台机器跑不了 |
| **内网地址** | 搜 `10.`、`192.168.`、`sit-`、`-test.` | 评委点开是超时，看起来像挂了 |
| **大数据文件** | `git count-objects -vH`、找 >10MB 的文件 | 仓库体积会拖慢 clone，也暴露原始数据 |
| **别人的东西** | 搜`作者名`、搜`往届`、看 `git log --format="%an"` | 混进别人项目的成绩/数据是硬伤（`06` §3.2 实测过） |

> **已经 push 过密钥怎么办**：改 `.gitignore` 没用，它只管未来。要么 `git filter-repo` 重写历史（25 分钟起），要么**换仓库**（10 分钟，且保证干净）。**黑客松里换仓库更快**——除非已经交了链接。

## 七、新机器验证：唯一诚实的检查

**做法：把仓库 clone 到另一个目录（最好换台机器 / 换个系统用户），删掉所有本地缓存，只照 README 敲。**

```bash
# 1. clone 到一个干净目录（模拟评委）
git clone --depth 1 <repo> /tmp/verify && cd /tmp/verify

# 2. 只看 README，不看别的。逐条敲
#    敲不过 = README 错了，不是环境错了

# 3. 跑到能看到界面 / 拿到响应为止

# 4. 顺手看体积和残留
du -sh .git
git ls-files | grep -iE "\.env$|\.pem$|\.key$|secret" || echo "无敏感文件"
```

**为什么必须新目录**：你本地的 `.venv`、`node_modules`、全局装的 CLI、你机器上的环境变量，全都不会跟着 clone 走。**你以为"三条命令能起来"，其实靠的是你机器上早就装好的东西。**

这一步最常暴露的四件事：

| 症状 | 说明 |
|---|---|
| `ModuleNotFoundError` | 依赖没写进 `requirements.txt`，只装在你机器上 |
| 端口 / 域名连不上 | 配置里写死了本机地址或内网地址 |
| 前端白屏 | 构建产物没提交，或 API base 写死成 `localhost` |
| 起来但功能报错 | 缺 `.env.example` 里的某个变量，README 没提 |

> **这一步的价值不在发现问题，在于它发现的问题都是评委一定会遇到的。** 你自己跑成功不算数——**别人跑成功才算**。

## 八、整理只做加减，不做搬家

**F 点之后，禁止改目录结构。** 这句话要写进 `AGENTS.md`。

原因很具体：仓库里所有**路径引用**都是硬编码的字符串。

| 你一改目录，这些同时断 | 断了的后果 |
|---|---|
| README / 结构文档里的路径 | 文档写的文件不存在，比没文档更糟 |
| 部署配置（`docker-compose.yml` 的 `context`、CI 的 `working-directory`） | 重新部署直接失败 |
| 代码里的 import / 相对路径 | 编译不过 |
| 决赛提交页里指向文件位置的链接 | 404 |
| `docs/` 里所有交叉引用 | 评委翻文档全部断链（本 skill 自己就踩过：文件搬家后 12 处引用全断） |

**F 点后允许的整理只有两类：**

- **加法**：补文档、补注释、补 `.env.example`、补 License
- **减法**：删死代码、删密钥、删大文件（**删了要全文搜一遍有没有引用**）

**搬家（移动 / 重命名目录）一律留到赛后。** 赛后的整理见 `16` §八。

## 九、提交前整理清单（照着打勾）

```markdown
## 清
- [ ] `git log -p --all -S "sk-"` / `-S "AKIA"` 无命中（或已吊销重发）
- [ ] 无 `.env`、`.pem`、`.key`、`credentials*` 入库
- [ ] 全仓搜不到 `C:\Users`、`/Users/`、`localhost:3000`、`127.0.0.1`、`10.` `192.168.`
- [ ] 无 `node_modules/` `.venv/` `dist/` `__pycache__/`
- [ ] 无 >10MB 的数据/权重文件（或已说明为什么必须在仓库里）
- [ ] 无注释掉的死代码块、无 `TODO` 占位
- [ ] **`git log --oneline | head -40` 读一遍：能看出做了什么，无 `update` `fix` `111` 这种无信息量 message**
- [ ] **无 WIP 半截提交**（有就 `git rebase -i` 合并，或至少保证 HEAD 能跑）
- [ ] **无 `--force` 覆盖痕迹**（`git log --all --oneline | wc -l` 与团队认知一致；有人丢过提交就查这里）

## 正
- [ ] 产品名在 README / 提交页 / 仓库名 / 页面标题四处一致
- [ ] 全仓搜 `example`，无 `github.com/example/*` 这类占位链接
- [ ] 环境变量名前后端一致，且都在 `.env.example` 里
- [ ] **脚本换行符正确**：`.githooks/` `*.sh` 是 LF，`*.bat` 是 CRLF（`.gitattributes` 生效了吗：`git ls-files --eol | head`）

## 补
- [ ] README 四段齐（一句话+图 / 怎么跑 / 验证结果 / 边界）
- [ ] `docs/architecture/项目结构.md` 七段齐
- [ ] `docs/README.md` 索引列全
- [ ] `LICENSE`（开源赛必须有，内部赛问主办方）
- [ ] `.env.example`（有配置就必须有）
- [ ] `.gitignore` 覆盖 `.env` `node_modules` `dist` `__pycache__` `.DS_Store`

## 验
- [ ] 新目录 clone → 只照 README 敲 → 能跑到出结果
- [ ] 主要功能跑一遍，输出与"验证结果"那节写的一致

## 锁
- [ ] 打 tag `v1.0`，提交页链接指向该 tag 而不是 `main`
- [ ] `git status` 干净，无未提交改动

## 点
- [ ] 无痕窗口（未登录）点开：仓库 / demo / 视频 / 文档，全部可访问
- [ ] 手机上再点一遍
- [ ] 视频链接剩余有效期 > 提交后 7 天（实测出现过 54 分钟后过期）
```

## 十、这套做法的边界

- **"七段"是从比赛提交材料反推的常见结构，不是某一份具体文档的原文。** 如果手上有一份赛道方给的范文，**以范文的章节顺序为准**——评分表对应的往往就是范文的目录。
- **A-2 就建结构文档骨架，在 2 人以下的小队里会显得多余。** 一个人写代码时，目录结构在自己脑子里。但只要队里出现第二个会改代码的人，就得建——否则他会自己另建一套。
- **90 分钟的整理时间，是"项目在 2000 行以内"的量级。** 超过这个量级，第 1 步的"清"会占掉大半时间，要提前一天做。
