# 14 · 仓库与远程协作

> 一句话：**本地目录要不要建，是你自己的事；远程仓库要不要建，是比赛规则的事。**
> 本地乱建只影响自己，远程建错（尤其公开/私有选错）可能直接违规。

---

## 一、建容器时问三个问题，不要默认建

A-0 建本地目录时，**同一次对话里问清这三件**，用户说不做就跳过：

| # | 问题 | 默认值 | 为什么要问 |
|---|---|---|---|
| 1 | **要不要推远程仓库？** | 要 | 有些赛只收 zip、不看仓库；也有人不想留公开痕迹 |
| 2 | **仓库叫什么名字？** | `<赛事缩写>-<产品名>` | 名字定了就不改——改名会让旧链接 404 |
| 3 | **公开还是私有？** | **公有**（除非规则要求私有） | 后两项的判据在 §二 |

**为什么必须在第 1 天问，而不是等到要提交时：**
- 远程仓库晚建 → 前面几天的 commit 时间线全丢，评委看到的 `git log` 只有最后 24 小时
- 如果规则要求私有，你要**从一开始就不往仓库里放不能公开的东西**（密钥、客户数据、内网地址）；事后清理要改历史，很容易漏

> **不要替用户默认公开。** 先问一句，成本 5 秒。

## 二、公开还是私有：先看规则，再谈习惯

### 判据顺序（按可靠度）

| 序 | 看什么 | 得到什么 |
|---|---|---|
| 1 | **参赛协议 / 规则正文**有没有"代码保密""成果归属主办方" | 有 → **必须私有**，没有商量 |
| 2 | **提交表单**有没有"源码仓库链接"字段 | 有 → **公有**最省事（评委直接点开） |
| 3 | **往届获奖项目**能不能搜到公开仓库 | 搜得到 → 该赛惯例是公有；搜不到 → 可能私有或没要求 |
| 4 | 提交表单要求"上传源码包 / zip" | 说明不看仓库 → 公开私有都行，按你意愿 |

### 三种赛制，三种答案

| 赛制 | 常见于 | 建议 | 理由 |
|---|---|---|---|
| **提交页有源码链接** | 大多数线上赛、开发者赛 | **公有** | 评委一键点开，没有邀请环节，没有过期风险 |
| **只看 demo / 视频，不看代码** | 商业类、路演类黑客松 | 公有（或私有都行） | 公有更省事，且赛后可当作品集 |
| **规则明确要求保密 / 代码归主办方** | 企业内赛、大厂闭门赛、涉数据合规的赛 | **私有** | 违规可能取消资格，这一条优先级高于一切 |

### 默认公有的三个实际理由

1. **公有零成本，私有有额度**：GitHub 公有仓库的 Actions 免费无限，私有仓库 Free 计划只有 2000 分钟/月。CI 跑得多会撞墙。
2. **私有在提交时多一道风险**：要邀请评委 → 评委没接受 → 链接打不开。而且**私有仓库对无权限者返回 404，不是 403**，看起来和"仓库不存在"一模一样，评委会直接判定你没交。
3. **公有仓库是作品集**：赛后可写进简历、可做二次传播。私有仓库赛后就废了。

> **唯一必须选私有的情况：规则写了。** 这时在 `docs/product/赛程卡.md` 记一行「本赛代码保密」，并在 G4 检查"是否已按规则提供访问方式（邀请评委 / 交 zip / 截止后开源）"。

## 三、团队赛的仓库怎么建

### 三种模型

| 模型 | 谁建 | 加人方式 | 适用 |
|---|---|---|---|
| **个人号 + Collaborator** | 队长本人账号 | Settings → Collaborators → 逐个邀请 | **3–5 人小队最常用**，够用且不折腾 |
| **GitHub Organization** | 新建一个 org | 建 Team，整队加进去；权限按 team 管 | 5 人以上，或想跨比赛复用同一套权限 |
| **主办方提供仓库** | 主办方建 | 主办方把你加进去 | 企业内赛常见，注意你可能没有 admin 权限 |

**建仓库的人 = 后面能改权限的人。** 不要用临时小号建，赛后想把仓库转到个人号或组织下很麻烦。

### 邀请是最容易漏的一步

| 坑 | 后果 |
|---|---|
| 发了邀请，对方没点接受 | 他以为加入了，`git push` 报 403 |
| 用邮箱邀请，但对方 GitHub 绑的是另一个邮箱 | 邀请发到一个不存在的账号 |
| 赛前 1 小时才发邀请 | 对方在通勤路上，到了现场才发现没权限 |

**规则：赛前一周发邀请，并要求每人回一句"已接受"。**

### 权限怎么给

| 角色 | 权限 | 理由 |
|---|---|---|
| 队长 | Admin | 唯一能改设置、加人、转移仓库的人 |
| 主程 | Write | 能推代码，不需要 Admin |
| 其余人 | Write | 比赛里没必要设 Read，会拖慢 |
| 外部/评委 | **不要加**。要公开就整体公开 | 逐个邀请评委会漏 |

## 四、分支与合并：分三阶段，不是一句话

**先纠正一个常见说法：「黑客松不要走 PR」。** 这句话在 48 小时里成立，在准备期不成立，而且它漏掉了一个收益——**PR 历史本身就是"这是团队做的"的证据**。

关键的前提变化：**GitHub 允许开 PR 之后自己点 Merge**（分支保护不要求 approval 时）。成本从"等别人 review"降到 90 秒，收益全保留。

### 三种模式，成本差多少

| 模式 | 一次耗时 | 留下什么 | 什么时候用 |
|---|---|---|---|
| **直推 `main`** | 30 秒 | 一条 commit | 只有 1 个人在改；或者 P=0 的临时赛 |
| **短分支 + 自己开 PR 自己合**（solo-merge） | **90 秒** | **一条 PR（带标题、diff、可一键 Revert）** | **默认推荐**，多数阶段都用这个 |
| **分支 + PR + 别人 review** | 20 分钟起（含等待） | 同上 + 评审记录 | 只在准备期、且改的是契约/架构 |

**90 秒买到什么**（这是推荐它的全部理由）：

1. **diff 自己过一遍**——直推时你根本不会看自己改了什么，PR 页面会逼你看
2. **一个可回滚的单位**——`Revert` 按钮一键撤，比 `git reset` 安全，也比在 5 个人头上 force push 安全
3. **冲突在合并前暴露**——直推时冲突在 push 那一刻才炸，那时你已经在赶时间
4. **PR 标题就是可读的历史**——评委（或三个月后的你）打开 PR 列表，能看懂这个项目做了什么

**24 小时里 40 次提交的账**：直推 20 分钟，solo-merge 60 分钟。**多花 40 分钟，买的是 F 点前出事故时能 30 秒回滚而不是 30 分钟定位。**

### 分阶段用哪一档

| 阶段 | 模式 | 为什么 |
|---|---|---|
| **建仓 → G2（准备期）** | **真 PR + 别人 review**（至少 1 次） | 有时间，且这是唯一能留下"协作真实发生"的机会 |
| **O 点 → F 点（现场）** | **短分支 + solo-merge**，**不等 review** | 分支名 `feat/xxx` `fix/xxx`，开完自己点 Merge，全程 90 秒 |
| **F 点 → 提交** | **只有一人能推 `main`**（见下） | 别人开 PR，合并权持有人 5 秒内点合 |

**现场唯一不许做的**：`git push --force` 到 `main`。多人协作时它会**覆盖别人的提交**，而且不可恢复。要撤回就 `git revert`（会多一条 commit，但历史是真的）。

### 合并权：只给一个人，但职责不是 review

**「管理员和谁合」的答案：合并权只归一个人，另配一个 backup。**

| 角色 | 权限 | 合并职责 | 为什么 |
|---|---|---|---|
| **合并权持有人**（队长或主程） | Admin | **5 秒内点 Merge**，不看代码 | 分散合并权 = 冲突解决成本指数上升 |
| **backup**（另一人） | Admin | 持有人睡觉/断网时接管 | 24 小时里一定有人不在线，单点会阻塞全队 |
| 其他人 | Write | 只开 PR，不合并 | 他们能推自己的分支，只是不能合进 `main` |

**这里最容易搞错的一件事**：黑客松里的"合并"不是 code review。**它的作用是"让主分支始终处于能跑的状态"，不是"审代码质量"。** 反过来做（每个 PR 都要读一遍）在 24 小时里会吃掉 3 小时以上。

> 如果队里只有一个人会写代码，合并权给谁？**给那个人，但任命一个"合并代理"**——代理不懂代码，只负责在他忙不过来时点按钮。这个人通常是队长，也正是路演讲稿的负责人（他本来就最关心"能不能跑"）。

### 服务端到底能约束到哪一层（实测）

你问的"提交时应该有约束"——先看能不能在服务端强制，因为**只有服务端强制才不依赖自觉**。

| 仓库类型 | 分支保护 / Rulesets | 来源 |
|---|---|---|
| **公开仓库**（任何计划，含 Free） | ✅ 免费可用 | GitHub Docs: rulesets 在 Free 的公开仓库可用 |
| **私有仓库 + Free** | ❌ **403**：`Upgrade to GitHub Pro or make this repository public` | 实测 `gh api repos/<owner>/<repo>/branches/main/protection` 返回这条 |
| **私有仓库 + Pro/Team** | ✅ 可用 | 同上文档 |

**这条直接改变了"公开还是私有"的权衡**（见 §二）：

- **公开** → 免费拿到服务端强制（禁止直推 main、禁止 force push）→ **有真约束**
- **私有 + 免费** → 服务端无法强制 → 只能靠下面的第 2、3 层

> **降级选项**：GitLab 的 protected branches **所有档位（含 Free）都有**，且默认分支默认受保护。如果规则要求私有仓库、又想要机制约束，**GitLab 比 GitHub Free 更合适**。GitHub 私有免费仓库在这件事上是真的做不到。

### 三层约束（从最强到最弱，按顺序装）

**第 1 层：服务端强制（公开仓库必装，2 分钟）**

GitHub → Settings → Rules → New ruleset → 目标分支 `main`：

| 开哪条 | 效果 |
|---|---|
| ✅ **Require a pull request before merging** | 任何人（含 admin）都得开 PR |
| ✅ **Block force pushes** | 禁止 `push --force` |
| ✅ **Restrict deletions** | 禁止删 `main` |
| ⬜ Require approvals | **不要开**。黑客松里会让自己无法合并，除非你把 approval 数设成 0 |
| ⬜ Require status checks | 只在 CI 真能跑通时开，否则会卡死所有人 |

**关键细节：把「合并权持有人」加进 bypass 列表。** 否则 F 点后出事故你想直接修，会被自己的规则挡住。这是"约束 + 留后门"的平衡——**约束的目的是防误操作，不是防救火**。

**第 2 层：仓库内配置（4 个文件，10 分钟）**

| 文件 | 作用 |
|---|---|
| `.github/pull_request_template.md` | 强制每次 PR 回答三个问题（改了什么 / 怎么验的 / 动了契约吗）。模板 `assets/.github/pull_request_template.md` |
| `.github/CODEOWNERS` | 按模块指定负责人，PR 自动提醒该找谁。模板 `assets/.github/CODEOWNERS` |
| `AGENTS.md` 的「提交规则」一节 | **让 AI agent 也遵守**——这是这套 skill 特有的一层，见下 |
| `README` 的「协作」一行 | 告诉评委"这个仓库怎么协作的"，比解释更有用 |

**第 3 层：本地 hook（不依赖付费，但可被绕过）**

`pre-push` 钩子在**推送前**拦下直推 `main` 的行为。两个文件放进仓库：

| 文件 | 作用 |
|---|---|
| `.githooks/pre-push` | 拦截逻辑（`assets/.githooks/pre-push`） |
| `scripts/install-hooks.sh` | 一条命令装好，幂等（`assets/scripts/install-hooks.sh`） |
| `.gitattributes` | **必须加**：`.githooks/* text eol=lf`，否则 Windows 上 checkout 成 CRLF，sh 报 `\r: command not found`，钩子静默失效 |

```bash
mkdir -p .githooks scripts
cp <skill>/assets/.githooks/pre-push .githooks/
cp <skill>/assets/scripts/install-hooks.sh scripts/
cp <skill>/assets/.gitattributes .
sh scripts/install-hooks.sh          # 装钩子（幂等）
```

**实测过的四种行为**（本机 Git Bash，2026-10-26 验证）：

| 场景 | 结果 |
|---|---|
| 首次 push（远端还没有 `main`） | ✅ 放行 —— 否则第 1 天就推不上去 |
| 远端已有 `main`，再直推 | ✅ 拦住，并打印正确做法 |
| `ALLOW_MAIN_PUSH=1 git push origin main` | ✅ 放行 |
| push 到 `feat/xxx` | ✅ 放行 |

**它必须带一个紧急通道**：`ALLOW_MAIN_PUSH=1 git push origin main`。理由——**hook 会在你最需要救火的时候挡路**，而 F 点后一定会有一次救火。没有紧急通道的 hook，最后会被 `rm` 掉。

> **钩子的诚实边界**：它存在 `.git/hooks` 或 `core.hooksPath`，**属于本地配置，不随 clone 走**。所以新队友必须跑一次 `sh scripts/install-hooks.sh`。这也是为什么第 1 层（服务端）不可省——**只有服务端强制才覆盖所有人和所有机器。**

**仓库里还有一层：PR 模板和 CODEOWNERS**

| 文件 | 作用 |
|---|---|
| `.github/pull_request_template.md` | 每次开 PR 自动带出三个必答项（改了什么 / 怎么验的 / 动了契约吗） |
| `.github/CODEOWNERS` | 按目录指定负责人，PR 自动提醒该找谁；冲突时知道找谁 |

模板在 `assets/.github/`。CODEOWNERS 里的 `@<用户名>` 换成真实账号，用不到的目录注释掉。

### AGENTS.md 里写什么（这一层是这套 skill 特有的）

人和 AI 都会在这个仓库里提交。**规则写进 `AGENTS.md`，AI agent 就会遵守；只写在聊天里，换个 agent 就忘了。**

最小一段（已包含在 `assets/AGENTS.md` 的「铁律」里）：

```markdown
7. **不直推 `main`。** 改代码走 `feat/xxx` `fix/xxx` 分支，开 PR，自己合。
   紧急情况（F 点后救火）用 `ALLOW_MAIN_PUSH=1 git push origin main`，并在 `flow/踩坑记录.md` 记一条为什么。
8. **F 点后 `main` 只许一个人推。** 其他人开 PR，由 <合并权持有人> 5 秒内合，不做 review。
9. **PR 标题带范围**：`feat(api): 加 /predict`。commit message 规范见 `09` §五。
```

### PR 标题顺手接上评分项

**免费的一步**：PR 标题末尾带评分项。

```
feat(demo): 一键生成周报 [完成度]
fix(auth): 修登录超时          [完成度/稳定性]
docs: 补证据表三条差评原文      [需求真实性]
```

这样 `git log` / PR 列表本身就是一张**评分映射的时间线**。评委如果翻仓库（很多会翻），他看到的不只是代码，还有"这个队知道自己在被怎么评"。

### 两条硬规定（沿用）

1. **`F 点`打 tag**（`v1.0`），提交页的链接指向 tag 而不是 `main`——否则你 F 点之后改崩了，评委看到的是崩的版本。
2. **F 点之后 `main` 必须可回滚**。出问题就 `git revert`，不要现场 `push --force`（多人协作时 force push 会覆盖别人的提交）。

### 一张图记住

```
准备期        现场 O→F           F→提交
真 PR+review  短分支+solo-merge   只队长推 main
  │              │                  │
  └─ 留协作证据  └─ 留可回滚单位     └─ 保住能跑的版本
```

## 五、现场网络：国内队伍的头号事故

**实测事实：从国内不挂代理推 GitHub，经常直接超时。** 这不是"慢"，是连不上。

| 对策 | 具体做法 | 时机 |
|---|---|---|
| **赛前配好代理** | `git config --global http.proxy http://127.0.0.1:<端口>`；验证：`curl -x http://127.0.0.1:<端口> -o /dev/null -w "%{http_code}" https://github.com` 返回 200 | **开赛前一周** |
| **双远程** | `origin` = GitHub，`backup` = Gitee；每次 `git push origin main && git push backup main` | 建仓库当天 |
| **降级方案** | 现场只本地 commit，收工前一次性推 | 前提：**赛前验证过"这一次能推成功"** |

> **不要在现场第一次配代理。** 典型事故：以为能推，结果花两小时调网络，等于白丢两个小时开发时间。

**另一个降级**：现场网络实在不行，就在提交页上传 zip，仓库链接留作"完整提交历史"的补充说明。但**先确认规则允许**。

## 六、提交链接的四个硬伤（实测踩过）

| # | 硬伤 | 后果 |
|---|---|---|
| 1 | 占位符链接（`github.com/example/xxx`、`your-repo`） | 评委点开 404，**这一项直接 0 分** |
| 2 | 私有仓库没加评委 | 同上，404（私有对无权限者返回 404，不是 403，看起来就是"不存在"） |
| 3 | 链接指向 `main` 而非 tag | 你后来改崩了，评委看到的是崩的版本 |
| 4 | README 没有"怎么跑" | 评委不会跑，等于没有 demo |

### 交稿前的机械检查

**每条链接用无痕窗口（未登录状态）打开一遍。**

原因：登录状态下你能看到自己的私有仓库、能看到自己 draft 的页面，**你会误以为所有人都能看到**。无痕窗口是唯一诚实的视角。

## 七、什么时候该做哪一步

> **提交前的整仓整理（清 → 正 → 补 → 验 → 锁 → 点）在 `15` §六，那一步比这里的建仓库更容易漏。**

| 时点 | 动作 |
|---|---|
| **第 1 天**（A-0） | 问三件事 → `git init` → `git remote add` → 首次 push |
| **第 1 天之后每次收工** | push（哪怕只改了文档） |
| **赛前一周** | 发 collaborator 邀请，要求每人回"已接受"；配好代理并验证 |
| **T-22** | 确认 CI 能跑（公有仓库 Actions 免费） |
| **F 点** | 打 tag `v1.0`；确认 `main` 可回滚 |
| **G4 交稿前** | 无痕窗口点一遍所有链接；确认私有/公有的选择符合规则 |

## 八、这套判断的边界

- **公开/私有的结论建立在"多数赛要求源码链接"上**，但**每个赛的规则不同，必须看当期规则原文**。本文件给的是判据顺序，不是通用答案。
- **代理端口每台机器不同**，文中 `<端口>` 是占位符。本机实测可用的是 `12334`（`curl -x http://127.0.0.1:12334 https://github.com` 返回 200），换机器要重测。
- **GitHub 私有仓库的 Actions 额度**（Free 计划 2000 分钟/月）会随计划调整，用时以当时页面为准。
