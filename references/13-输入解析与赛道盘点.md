# 13 · 输入解析与赛道盘点：从一条链接到一份能打的判断

> 前面 `08` 讲的是"怎么给一个赛道打分"，这份讲**在打分之前**：你手上只有一条链接、一张截图、一个群聊记录或一台实物时，怎么把它变成"我该打哪个、要几个人、还缺什么"。
>
> 这份文件的位置：**在 `08` 之前，在 `02` 之前。** 它是整套流程唯一一个"从零输入"的入口。

---

## 零、这一份要解决的三件事

| 你手上的状态 | 这一份给你 |
|---|---|
| 刚知道有这个比赛，只有个网址 | 30 分钟抽出"能不能打、打什么、要几个人" |
| 有 4 个赛道，不知道选哪个 | 一次评完，出排序 + 每个赛道的建议 |
| 赛道定了，不知道要什么人和技能 | 从演示链路反推环节、人数、技能缺口 |

**三件事的顺序不能反。** 先判谁能办（主办方动机），再判有几个格子（赛道盘点），最后判要几个人（资源与技能反推）。**反了就变成"先凑人再找题"，人越多越乱。**

---

## 一、开局：你手上有什么，能抽出什么

### 1.1 六类输入，各抽什么

| 输入形态 | 必抽的字段 | 抽不到的 | 最常见的坑 |
|---|---|---|---|
| **① 比赛官网 / 报名页** | 报名开止、**提交截止（到分）**、时长、线上线下、人数规则、赛道列表、奖项设置、提交入口 URL | 评审方式、评分维度 | 宣传稿的截止时间和报名页不一致。**以报名页为准，截图存证** |
| **② 赛道说明 / 赛题文档** | 每个赛道的"必须用什么"、"要交什么"、"**明确不评什么**" | 权重、及格线 | 约束藏在 FAQ / 答疑里，不在正文。**必须翻 FAQ** |
| **③ 评分表 / 评审规则** | 维度名 + 权重 + **每一档的描述** | 拿到时间 | 只看维度名不看档位描述，就不知道"及格线在哪"。档位描述里写着评委怎么区分 80 分和 90 分 |
| **④ 往届获奖作品** | 题目、产品形态、技术栈、**文档目录结构**、演示视频时长 | 他们的评分 | 只看获奖名单不看作品本身。**作品里能看出评委的口味** |
| **⑤ 群聊 / 主办方答疑** | 主办方实名回答的口径、资源发放方式、隐性规则 | 一致性 | 群里说的和文档写的不一致时，**以群里主办方实名回答为准**，但必须截图 |
| **⑥ 实物**（硬件 / 内部系统截图 / 数据集） | 接口、限制、已有数据、能不能改 | 归属与免责 | 能不能带走、能不能刷自己的固件、坏了谁赔。**这三条不问清，现场就是砖头** |

### 1.2 解析顺序（这条比抽什么更重要）

```
先找三个日期  →  再找赛道列表  →  再找"必须用什么"  →  最后才看技术细节
（能不能参加）    （有几个格子）    （资源约束）         （选型）
```

**为什么不能倒过来。** 技术细节最好看，最容易一头扎进去，看完两小时才发现"报名三天前就截止了"或"这个赛道必须用他们的云"。**能参加 > 打哪个 > 怎么做**，这三层的信息价值是递减的，但抓人注意力的能力是递增的。

### 1.3 抽不到就列"待问清单"，不要猜

**必须在 48 小时内问主办方的七件事**（问完贴进 `docs/product/赛程卡.md`）：

| # | 问什么 | 为什么不能猜 |
|---|---|---|
| 1 | 评分维度、权重、每档描述，什么时候能给？ | 决定你 S0 做多重（见 `12`） |
| 2 | **预赛和决赛是同一套评分表吗？** | 多数赛制是两套且不同时给。按一套准备，进决赛要重做一遍 |
| 3 | 这个赛道**必须使用**什么？（指定 SDK / 云 / 硬件 / 数据集） | 决定资源申请和选型，晚一天就少一天 |
| 4 | 交付物**必须包含**什么？（仓库 / 视频 / 部署地址 / 商业计划 / 现场 demo） | 少交一样等于这一项零分 |
| 5 | 现场网络和电源？（多人同时连 / 有没有有线 / 带宽） | 酒店 WiFi 3000ms 下所有联调都是假的 |
| 6 | 硬件 / 数据 / SDK 什么时候发、怎么申请、**能不能提前拿** | 提前一周拿到 = 多一周预埋；现场拿到 = 只剩 2 小时 |
| 7 | 提交入口在哪、**截止是几点几分、按什么时区**、能不能改 | 有人因为入口搞错被判无效 |

> 问的方式：一次问完，不要一条一条挤。**"我们想认真准备，有七个问题想确认"** 比 "在吗" 有效十倍。

### 1.4 素材到手：30 分钟核验盒（硬上限）

**主办方给了素材包、数据集、历史单据、示例仓库时，最危险的不是读不懂，是读得太深。**

深读的产出是"我把数据跑通了"，而这一步要回答的是"**这个题能不能打**"。两件事都会让人觉得自己在进步，但只有前者有即时反馈——所以人会一路滑过去，滑到 G1 之前就开始写解析脚本，而且**不觉得自己在犯错**。

**30 分钟只做三件事：清单 / 三问 / 一个结论。**

| # | 做什么 | 产出写在哪 |
|---|---|---|
| 1 | **清单**：几个文件、什么格式、总量多大、**有没有文本层**（可读 vs 纯扫描） | `docs/product/素材实测.md` 第一节 |
| 2 | **三问**：① 够不够做一次完整判断 ② 有没有自带基线（现成汇总值 / 预算价 / 合格线）③ **缺的是哪一类**——数据、口径、还是人 | 同上 |
| 3 | **一个结论**：一句话写"这些材料能支撑【X】，支撑不了【Y】" | 同上，加进 `赛道盘点.md` 的资源维度 |

**三个停止信号**（出现任意一个，立刻停手，把剩下的事记进 `flow/plan.md` 的 S3）：

| 你心里冒出来的话 | 它其实是 |
|---|---|
| "我写个脚本把它解析出来" | **S3 预埋** |
| "顺手把汇总数复算一遍，看对不对" | **S3 预埋 + 断言**（属于 `claims.md`，不属于这里） |
| "先算个均价 / 做个画像，好判断值不值得做" | **最像需求分析，实际是供给侧统计**——它回答"数据能算出什么"，不回答"有人为此付钱" |

第三行是实测踩过的坑：**它长得最像调研**，因为输出的是一张有洞察感的表。

**如果三问的答案是"缺人"**：30 分钟核验必须立刻结束，转去做差评与访谈。**素材再好也补不了"没人在痛"。**

越界了怎么止损（四步）见 `00` §四·补。

### 1.4·补 拿到历史单据 / 示例数据时的四条核验纪律

主办方给的不总是干净数据集，更多是**历史单据、往届提交、示例仓库**这类"半成品材料"。除了上面的清单与三问，还有四条纪律（2026-10 外部实证吸收）：

| 纪律 | 具体做法 | 反面 |
|---|---|---|
| **版本指纹** | 每个文件记 SHA256 前 8 位，写进 `素材实测.md`；核验结论与指纹绑定 | 一周后材料被替换，你的结论对不上任何一份现存文件 |
| **三列呈现** | 每一条核对发现写成三列：**原文写什么 / 计算发现什么 / 谁需要确认**。第三列空着 = 你替别人做了决定 | 只写"发现 3 处不一致"——不一致归谁管、问谁，全丢 |
| **时间泄漏** | 做历史决策复盘时，**只用决策时点已知的信息**。用事后才知道的结果去评价当时的决策，是时间泄漏——它让所有"当时应该"都变成废话 | "他们 2024 年就该选 B 方案"——B 方案的优势 2025 年才显现 |
| **标签 ≠ 事实** | 文件上贴的标签（"最终版""已审核""完整数据"）只是线索，**以内容为准**；标签与内容冲突时，两个都记，不自行选一个 | 照着"最终版"的标签分析，其实那份是草稿 |

**共同点：四条都在防"把材料的表面当成材料的本体"。** 材料核验盒的价值不是"读完"，是"知道自己读到的是第几层"。

## 二、主办方动机：五种赛，五种赢法

**这是整份文件里最省时间的一节。** 同一份方案，在"企业招人型"赛里能赢，在"投资招商型"赛里会输——不是因为做得不好，是因为**评委在打分时想的是完全不同的问题**。

### 2.1 五型对照

| 类型 | 办赛的真实动机 | 赛题性质 | 评委是谁 | 赢了得到什么 | 选题偏置 |
|---|---|---|---|---|---|
| **A 企业招人型** | 提前锁定候选人 + 内部创新点子 | 半开放，围绕自家业务 | 业务线负责人 + HR + 技术专家 | offer / 实习 / 内推 | **可落地 > 有想象力**。要能答"这东西我们业务线怎么用" |
| **B 企业生态型** | 推广自家技术栈 / 云 / 硬件，养开发者 | 常绑定自家 SDK 或平台 | 布道师 + 技术总监 | 云资源 / 硬件 / 生态合作 / 曝光 | **顺着它的技术栈做**，且要能被当成案例 | 
| **C 投资招商型** | 找项目（deal flow）+ 地方招商落地 | 全开放 | VC 合伙人 + 产业基金 + 政府 | 投资意向 / 落地补贴 / 媒体 | **市场空间 > 技术深度**。要能答"做大长什么样" |
| **D 社区技术型**（Kaggle / 天池） | 找方案 + 生态活跃 | **强约束**（数据集固定、指标固定） | 排行榜，不看嘴 | 奖金 + 排名 + 曝光 | **纯性能**。讲故事零分，别浪费时间写 PRV |
| **E 政府 / 国企命题型** | 采购前的方案征集 + 示范项目 | **强约束**（命题作文） | 业务部门 + 外部专家 | 试点采购 / 示范项目 | **贴着命题写**，发散即扣分 |

### 2.2 怎么判是哪一型（五条证据，按靠谱度排序）

| 排序 | 证据 | 怎么读 |
|---|---|---|
| 1 | **往届获奖者后来怎么了** | 拿到投资 / 入职主办方 / 变成采购合同 —— 这是最硬的证据，动机骗不了结果 |
| 2 | **奖品形态** | 现金 → C/E 型；offer / 实习 → A 型；云资源 / 硬件 / SDK → B 型；排行榜奖金 → D 型 |
| 3 | **评委名单的 title** | VC 合伙人 → C 型；CTO / 技术总监 → A/B 型；教授 → 学术型；业务部门负责人 → E 型 |
| 4 | 赛题是否绑定自家产品 | 绑 → B 型；不绑但给资源 → A 型；完全不提 → C 型 |
| 5 | 有没有"赛后落地条款" | 有孵化 / 投资 / 试点条款 → C/E 型 |

**五种证据里，只用一条会误判。** 典型误判：一场企业办的赛，奖品是现金（像 C 型），但评委全是自家业务线总监、往届获奖者都入职了（A 型）——**现金只是预算科目，不是动机**。

### 2.3 如果判成 C 型（投资招商）：再往下查一层

投资机构"投什么"是周期性的，会过时。所以这里给**稳定的框架 + 必查的三处**。

**稳定的部分——评委在 5 分钟里其实只想知道五件事：**

| 问题 | 他们真正在排除什么 | 你怎么回答 |
|---|---|---|
| **为什么是现在？** | 三年前做不了 / 三年后不用做 | 说清"什么变了"（成本降了 / 政策开了 / 模型能力到了） |
| **为什么是你们？** | 大厂一做你就死 | 说清独占的东西（数据 / 场景入口 / 行业关系 / 已经跑起来的东西） |
| **做到 10 倍大长什么样？** | 只是个工具，天花板很低 | 给"从 X 到 X×10"的路径，不是愿望 |
| **谁付钱、付多少？** | To C 免费 + 靠融资活 | 一句说清付费方和单价，哪怕是估算 |
| **别人抄你，你剩下什么？** | 纯 prompt 套壳、纯 UI 差异 | 说清沉淀（数据 / 网络效应 / 切换成本 / 合规资质） |

**易变的部分——具体偏好必须当期查，三处：**

1. 评委所在基金的**官网 portfolio 页**：他们已经投了什么 → 说明看得懂什么；没投什么 → 可能是盲区也可能是不要
2. 该基金**近 6 个月的投资新闻 / 公众号**：现在在押什么
3. 该合伙人的**公开访谈 / 播客**：他自己怎么说"我们在看什么"

> **不要用"AI 应用层 / 硬件+AI / 出海"这类词直接当选型依据。** 这些词半年就换一轮，且所有 VC 都说。要看的是**这一家**最近真金白银投了什么。

**C 型赛的反感清单**（讲了会掉分）：纯工具无壁垒 / To C 免费靠补贴 / 需要教育市场三年 / 只有 demo 没有付费方 / 把"技术先进"当卖点。

### 2.4 同一份方案，两种改写（这一张表最实用）

**内容不用改，开头和结尾必须改。**

| 环节 | A/B 型（企业） | C 型（投资） |
|---|---|---|
| 前 30 秒 | "这解决了**你们** XX 业务线的 XX 问题" | "这是一个 XX 规模的市场，现在没人做好" |
| 技术深度 | **深**。要能答实现细节（他们在评估你的工程能力） | **浅**。够证明可行即可（他们在评估商业判断） |
| 团队介绍 | "我们能落地，能进你们业务线" | "我们互补，能全职干这件事" |
| 数据 | 内部指标（效率 / 成本 / 工时） | 市场指标（付费方 / 单价 / 留存 / 获客） |
| 加分的部分 | 复用主办方已有的系统 / 数据 | 已经有的早期验证（哪怕 5 个用户） |
| 结尾 | "希望加入 / 希望合作" | "我们要用这笔钱做 Y" |
| 致命问题 | "这东西我们自己也能做" | "这东西做大了别人抄你怎么办" |

> 判错类型的代价：**在 A 型赛里讲市场空间，评委会觉得你空；在 C 型赛里讲技术细节，评委会觉得你只是个工程师。**

## 二·补、赛道背后的投资方：每个赛道都有一个"出题人"

**多赛道比赛里，每个赛道通常对应一个投资方、事业部或命题方。** 整场可能只有一套评分表，但评委席上坐着那个赛道的人——**他打分时想的是"这东西对我有没有用"，不是"这东西技术难不难"。**

所以判断顺序要改：不是"我能不能做这个题"，而是"**这个题背后是谁，它自己现在被什么卡住**"。

### 每个赛道问四件事

| 问什么 | 为什么它决定分数 | 去哪查（按可操作性排序） |
|---|---|---|
| **主营业务** | 靠什么赚钱就护着什么。你的方案动它的主业，再酷也会被压分 | 年报 / 招股书的业务分部、官网产品线、财报电话会 |
| **关注的点** | 它今年对外反复讲的那个词，通常就是它的 KPI（份额、毛利、合规、第二曲线） | 近 12 个月发布会、公众号、白皮书、CEO 访谈 |
| **要解决的问题** | 它公开承认的痛点，比你自己猜的需求可信十倍 | 年报"风险因素"、招聘 JD（在招什么岗 = 在建什么能力）、近两年专利、招标公告 |
| **所处领域的位置** | 领先者在防守、追赶者在找故事、新进入者在找切口——三种位置要三种方案 | 市场份额 / 出货量排名、它自己宣称的"第几" |

### 三种位置，三套打法

| 它的位置 | 它最怕什么 | 你的方案该长什么样 | 路演时该说哪句 |
|---|---|---|---|
| **领先者**（份额第一） | 被新玩法绕过、被合规卡住 | 加固它的护城河：更稳、更合规、更省成本 | "这能让你们的存量客户不流失" |
| **追赶者** | 追不上第一，且没有新故事 | 帮它讲一个"差异化"的故事，且 24h 能演出来 | "这是能对外说的那个新说法" |
| **新进入者 / 第二曲线** | 从 0 到 1 找不到切入点 | 给它一个能立刻试的小切口，不求大 | "这个切口下周就能做试点" |

**核心判据：你的方案解决的问题，正好是赛道投资方今年的 KPI → 评分会明显上浮。** 不是你讲得好，是他终于等到一个能写进汇报的东西。

**反向判据：如果方案让它的主营业务"被替代"，技术上再领先也会被压分。** 没有人会给自己被判死刑的方案打高分，哪怕它挂着"创新"的名义。

### 产出一张表（和赛道盘点放一起）

| 赛道 | 背后是谁 | 主营业务 | 它今年的痛点（带证据） | 我们的方案对上哪一条 | 对上之后它能写进什么汇报 |
|---|---|---|---|---|---|
| | | | | | |

最后一列别嫌虚——**评委也是要回去汇报的**。你能替他想好那句汇报词，他给你的分就高。

### 两个反例

1. **把"投其所好"做成"猜评委喜好"**：编一套"他们一定关心 X"的说法，没有任何出处。正确做法是**拿它公开说过的话当靶子**，把链接贴进赛道盘点表。
2. **只查投资机构，不查产业方**：A/B 型企业赛里的"投资方"其实是事业部，它的 KPI 是内部的（人力成本、交付周期、良率），不是市场规模。**查错对象，整张表作废。**

> 和 `02` §五 的关系：这里说的"投资方"就是这场比赛里最真实的**付费者 + 决策者**。`02` 教你写"谁付钱、为什么是我们"，这一节教你在**比赛语境里先找到那个人是谁**。

## 三、多赛道盘点：一次评 N 个，出排序和建议

### 3.1 为什么必须批量评

单看一个赛道，越看越觉得能做——这是**沉没注意力的偏差**。只有把 N 个放在同一张表里横向比，"它其实是个坑"才看得出来。

### 3.2 五步流程（拿到赛道列表后 4 小时内做完）

| 步 | 动作 | 耗时 | 产出 |
|---|---|---|---|
| **① 抄全** | 把**所有**赛道名一字不差抄下来，包括你认为不可能的 | 20 min | 赛道总表（空行） |
| **② 减法** | 先删掉三类明显不可能的（见 3.3） | 30 min | 剩余候选（通常 5 个赛只剩 2–3 个） |
| **③ 打分** | 五维打分（`08` §一），**只给剩下的打** | 90 min | 分数表 |
| **④ 动机 + 投资方匹配** | 每个赛道标两件事：它在五种主办方动机里偏哪型；它背后是谁、那人今年的痛点是什么（见 §二·补） | 60 min | 匹配度判断 + **投资方地图** |
| **⑤ 排序出建议** | 排序 + **每个赛道一句话建议（打 / 不打 / 备选 + 理由）** | 40 min | 决策 |

### 3.3 先做减法：三类直接删

| 类型 | 判据 | 为什么先删 |
|---|---|---|
| **资源拿不到** | 必须用某硬件 / 数据 / 资质，而你申请不到或赛前拿不到 | 这不是"难"，是"不可能"。留着它会污染后面的比较 |
| **演不出来** | 想不出"10 秒能演完的画面" | 想不出画面 = 24 小时做出来也讲不清 |
| **存量为零且学不完** | 核心技术你完全不懂，且需要 > 20 小时才能到"能演示" | S3 只有 5 天，学不完 |

**减法要在打分之前做。** 先打分再删，你会不自觉地给"想打的那个"打高分。

### 3.4 判据修正：多赛道下不看总分

单赛道时看"有没有单项 ≤ 2"。**多赛道横向比时，看有没有哪个赛道出现"三项 ≥ 4"**：

| 情形 | 结论 |
|---|---|
| 有一个赛道 **三项 ≥ 4** | **就是它。** 三项强的赛道，剩下的两项可以靠队友补 |
| 全部赛道都是"两项 4、三项 3" | 没有明显优势 → **换打单项奖**（`08` §二赛制套利），或重新看有没有漏掉的赛道 |
| 最好的赛道也有单项 ≤ 2 | **别打这个比赛**，或者打一个"只为练手"的心态 |

> 加权总分的陷阱：一个赛道 30% 权重拿 5 分、其余拿 2 分，总分可能和"全是 3 分"的赛道一样。**但前者能在 24 小时里做出东西，后者做不出。** 权重是给"已经能做"的人排序用的，不是给"能不能做"用的。

### 3.5 每个赛道必须写一句"建议"，不许只给分

**只给分的评估没有决策价值。** 建议必须三选一，且带理由：

```
赛道 A（智能硬件）：建议打。资源独占 + 演示可见性 5 分，存量 3 分可补。
赛道 B（Agent 应用）：不打。竞争密度最高，且我们的存量优势在这个赛道不构成差异。
赛道 C（数据洞察）：备选。若 A 的硬件赛前拿不到，切 C，切换成本 1 天。
```

**"备选"必须写清触发条件和切换成本。** 否则开赛发现选错时，没人敢切。

模板：`assets/docs/赛道盘点.md`

### 3.6 三个常见误判

| 误判 | 表现 | 纠正 |
|---|---|---|
| **按技术热度选** | "大模型赛道最有前途" | 热度 = 竞争者最多。**热门技术 + 冷门场景**优于冷门技术 + 热门场景 |
| **按自己擅长选** | "我做后端十年，就打后端赛道" | 擅长是迁移的，不是绑定赛道的。**把能力迁到有资源的赛道** |
| **按奖金高低选** | "大奖 10 万，就打大奖" | 奖金高的格子竞争强度是平方级上升的。算 `合格竞争者数`（`08` §二） |

## 四、从赛道反推：资源、人数、技能

### 4.1 先列资源，再列人

**顺序不能反。** 先想"要几个人"会得到"越多越好"；先列"这条链路需要什么资源"，人数是从链路里数出来的。

| 资源类 | 具体问 | 没有它的后果 | 兜底 |
|---|---|---|---|
| **硬件** | 主办方给吗？什么时候给？能不能提前拿？ | 现场 2 小时调试，基本做不成 | 赛前自己买同型号（贵但保命） |
| **SDK / API / 云** | 必须用吗？有额度限制吗？审核要多久？ | 现场发现要企业认证 → 卡 1 天 | 赛前把账号、认证、配额全办好 |
| **数据** | 主办方给真实数据吗？能导出吗？有隐私限制吗？ | 只能造假数据，一被追问就崩 | 用公开数据 + 明说"这是公开数据" |
| **专家 / 内部人** | 现场能找到懂业务的人问吗？ | 做出来的东西业务上不成立 | 赛前找 1 个行业内的人做 30 分钟访谈 |

> **资源表要写成"没有它能不能演"**，不是"有没有"。能演的才是可选项，不能演的是前置条件——**前置条件在 S3 之前必须到手**。

### 4.2 人数 = 独立交付环节 + 1

**"独立交付环节"的定义**（比 `08` 的"独立环节"更严）：画一遍演示链路，**每一个必须单独跑起来、且不能被同一个人在同一时段并行完成的节点，算一个环节**。

```
例：手机 App + 后端 + 算法
  App 界面（1）── 后端 API（2）── 算法/模型（3）── 队长（协调 + 路演 + 兜底）
  = 4 人

例：Web 工具
  前端（1）── 后端（2）── 队长
  = 3 人（前端和后端可以是一个人，但那样就没有冗余，出问题没人接）
```

**三条边界：**

| 边界 | 数法 |
|---|---|
| 安卓 + iOS 各一人 | **算 2 个环节**，因为代码不能复用。这是唯一能让人数破 5 的理由 |
| 硬件 + 固件 + App | 固件和 App **算 2 个**（不同工具链），硬件本身算 1 个 |
| 纯 Agent / API | **只算 1 个环节**，但必须配一个壳 → +1 界面 |

**减法判据**：如果你数出来 > 6 人，**不是人多，是链路太长**——回去砍 P0（`03` §4.2），把环节数压到 4 以内。

### 4.3 技能分级：不是"会/不会"，是"6 小时能不能交出能演的版本"

| 级别 | 定义 | 能承担什么 |
|---|---|---|
| **L3 能独立交付** | 独立做过完整上线的同类东西，能答"为什么这么选" | 主责该环节，且能带人 |
| **L2 能改** | 会改现成项目，但自己搭不出来 | 在主责指导下做，不能独立顶 |
| **L1 学过** | 上过课 / 写过后端 demo，没上线过 | 只能做辅助，**不能算作一个环节的人** |
| **L0 不会** | — | 要么学，要么砍，要么找人 |

**最容易犯的错：把 L1 当 L2 排进链路。** 24 小时里 L1 的实际产出是 0，且会吃掉一个 L2 的时间去救他。

### 4.4 能力矩阵：一张表看清缺口

模板（填进 `flow/team.md`）：

| 演示链路的环节 | 需要的技能（具体到工具） | 队里谁能 L3 | 谁能 L2 | 缺口 | 处理 |
|---|---|---|---|---|---|
| 前端界面 | React + 图表库 | 张三 | 李四 | 无 | — |
| 后端 API | FastAPI + Redis | 王五 | — | 无 | — |
| 算法 | 时序预测 | — | 王五 | **L3 缺** | 砍成规则版 / 找外援 / 用现成库 |
| 现场部署 | Docker + 域名 | — | 张三 | 有风险 | 赛前一周张三专练一次 |
| 路演 / 视频 | 剪映 + 讲稿 | 赵六 | — | 无 | — |

### 4.5 缺口的三种处理（按优先级）

| 处理 | 什么时候用 | 代价 |
|---|---|---|
| **① 砍掉换形态** | 缺的环节不是 P0 必需的 | 0，且立刻生效。**优先选这个** |
| **② 用现成库 / AI 生成** | 缺口是"实现"不是"判断" | 半天到一天，且要留兜底 |
| **③ 找人补** | 缺口是 P0 且无法替代 | 3–7 天（找人 + 磨合），**赛前 1 周内找不到就别找了** |

> **反模式：为了一个环节去招人。** 招来的人磨合要 2 天，且他大概率不了解前情。**先砍环节，再找人。**

## 五、人员定序：谁先定、谁后定

**这是"人员先定还是后定"的答案：分三层，不是一次性决定。**

**用绝对锚点，不用 T 数字**——因为短的赛根本没到 T-25：

```
第 1 天 ────── 队长（1人）─────────────── 决定"打不打"
                  ↓
第 3 天内 ──── 核心二人（队长 + 主程）──── 决定"能不能做"（打完五维分的存量项）
                  ↓
开赛前 5 天 ── 其余人（按环节数补）─────── 决定"做多快"（选完赛道才知道要几个人）
```

| 锚点 | L 档（P≥25 天）对应 | P 很小时怎么办 |
|---|---|---|
| 第 1 天 | ≈ T-30 | 不变（**这一层与赛程长度无关**） |
| 第 3 天内 | ≈ T-25 | 不变（3 天是硬上限，P=3 也要在第 3 天定完） |
| 开赛前 5 天 | ≈ T-18 | P < 5 时就是"开赛前"，最晚开赛前 1 天 |

> **为什么前两层不用换算**：队长和核心二人是"能不能打"的前提，不是"打得多快"的变量。哪怕 P=2 天，也得当天定队长、次日前定主程——否则五维打分算不出来。

### 5.1 为什么核心二人必须先定

**因为五维打分里"存量可复用 20%"这一项，打分主体是团队，不是赛道。**

没有主程，你没法判断"这个赛道的存量能复用几成"——你只能猜。而这一项恰恰是**唯一一项你能自己改变**的（其余四项是外部条件）。

所以：
- **队长 + 主程到位前，五维打分是失效的**，只能做排除法（`§3.3` 三类直接删）
- 队长 + 主程到位后，才有资格做 `§3.4` 的"三项 ≥ 4"判断

### 5.2 为什么其余人必须后定

**因为人数 = 独立环节 + 1，而环节数取决于赛道的技术形态**（`§4.2`）。

- 选 Web 工具 → 3 人
- 选 App + 后端 + 算法 → 4 人
- 选硬件 + App + 云 + 算法 → 5 人

**先凑 5 个人再选赛道，会发生两件事**：① 多出来的 2 个人会自己造需求（"我可以做个管理后台"）；② 你会不自觉地选一个"能容纳 5 个人"的赛道，而不是"最容易赢"的赛道。

### 5.3 三种特殊情形

| 情形 | 定序怎么改 |
|---|---|
| **只有你一个人** | 五维权重改成"存量 40% / 可见性 30% / 资源 20% / 竞争 10%"。变成**赛道迁就能力**，且必须选 Web 或纯 Agent 形态 |
| **公司内部组队，人是分配的** | 反过来：**先做能力盘点（4.4），再选赛道**。赛道必须在"能力矩阵覆盖 ≥ 80%"的范围内选 |
| **跨公司 / 跨校拼队** | 核心二人必须在**第 3 天内**定，且**必须赛前见过面**（线上也行，但要一起干过 2 小时活）。纯线上认识的队，现场第一小时会浪费在互相试探 |

### 5.4 定完人数后的第一个动作

不是分工，是**列未认领清单**（`SKILL.md` §三①）。

分工表写"谁做什么"，未认领写"没人做什么"。**人定完的那一刻，是唯一一次能看清"哪些事没有主人"的时刻。** 过了这一小时，每个人都会以为自己负责的范围已经覆盖了全部。
