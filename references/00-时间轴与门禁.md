# 00 · 时间轴与门禁

> 目标：把"打一场比赛"变成一张可以照着走的日程，每个阶段都有产出物和过门条件。
> 用法：开工先看这张表定日程，再按阶段读对应详规。

---

## 零、先算三个数，再选骨架

> **T-30 不是通用水位，是「准备期 ≥25 天」这一档的默认值。** 很多黑客松从报名到提交只有 5–7 天，照抄 T-30 会算出「T-22 已经在比赛之后」这种荒谬日程。

### 三个记号

| 记号 | 含义 | 怎么算 |
|---|---|---|
| **D** | 距提交截止还剩几天 | 提交截止 − 今天 |
| **H** | 比赛时长（小时） | 24 / 36 / 48 / 72 |
| **P** | **纯准备期天数** | `P = D − H ÷ 24` |

**P 才是决定用哪套骨架的那个数。**

> 例：一场 48h 线上赛，今天距提交截止还有 7 天 → `D=7, H=48 → P=5`。这是 X 档（超短），不是 L 档。

> **T-n 的统一含义：距提交截止 n 天。** 报名截止**不是** T-0，它是中间的一个检查点 `R`——不报名全盘作废，但它不是倒计时原点。当 `D < 30` 时，`T-30` 这个点在你的赛程里**根本不存在**，不要硬套。

### 六档骨架：P 决定用哪套

| 档 | P（纯准备期） | 典型赛制 | 用哪套骨架 |
|---|---|---|---|
| **L 长** | **≥ 25 天** | 42 天赛程（含预赛型）、多轮预赛 | 本文件 §二~§九 的完整 S-1 → S6 |
| **M 中** | 14 – 24 天 | 三周线上赛 | L 档压缩：砍往届作品研究，S0 压到 4 天，S2 压到 3 天 |
| **S 短** | 7 – 13 天 | 十天线上赛 / 有预赛的短赛 | 只做五件事，预赛文档砍到 4 章（见下） |
| **X 超短** | 3 – 6 天 | 一周内完成的线上赛 | **只做三件事**：容器 / 报名 / 选题 |
| **T 临时** | 1 – 2 天 | 朋友拉你入队 | **只做两件事**：容器 + 选题，其余移到 O 点后 |
| **Z 现场** | 0 天（现场才决定） | 现场报名 / 当天下场 | 开赛前 1 小时建容器，逆向+选题压到 30 分钟 |

**各档的具体日程：**

- **L / M**：读 §二~§九，按阶段推进。
- **S（7–13 天）**：
  | 天 | 做什么 | 砍掉什么 |
  |---|---|---|
  | D1 | 建容器（30min）+ 报名 + 评分逆向 + 选题，**当天过 G1** | 往届作品细节 |
  | D2–D3 | 调研（二手为主）+ 预赛文档只写 4 章 | 一手访谈、设备实测 |
  | D4 | 拿资源 + 预埋链路 | —（**这是唯一不能砍的**） |
  | D5 | 预埋部署，当天必须通 | — |
  | D6 | 契约冻结，过 G2 | 完整架构文档 |
  | D7 | 彩排 + 物料 | 多版路演稿，只留一版 |
- **X（3–6 天）**：D1 容器+报名+逆向+选题（当天过 G1）；D2 资源+链路；D3 部署打通；D4–D5 主链路 + 物料。**没有预赛文档，除非它决定你能不能进决赛。**
- **T（1–2 天）**：今天建容器 + 定题 + 确认提交入口；明天拿资源 + 打通部署。**目标从"拿名次"降为"完整交付"。**
- **Z（0 天）**：开赛前 1h 建容器（`git init` + `flow/` + `docs/`），前 30min 做逆向+选题。**不要试图现场补调研，借主办方给的资源和赛题原文。**

### 不管哪一档，这四件都不能砍

| 动作 | 成本 | 砍了会怎样 |
|---|---|---|
| **建容器** | 30 min | 全部产物落回聊天记录，交付时找不回 |
| **报名** | 5 min | 前面全白做 |
| **评分表逆向** | 60 min | 努力方向随机，做完才发现不踩分 |
| **选题减法**（三类直接删） | 30 min | 在注定做不出的题上花光全部时间 |

**合计约 2 小时。** 任何档位都拿得出这 2 小时——包括 P=0 的现场赛。

### 时间不够时，按这个顺序砍

1. **往届作品研究**（省 1–3 天）
2. **八点商业论证 → 只留三点**：为什么是现在 / 谁付钱 / 市场多大（省 2 天）
3. **一手访谈 / 设备实测 → 改二手**（差评、工单、论坛。省 3 天，但证据等级降一级，**必须在文档里明说**）
4. **预赛文档 → 只写 4 章**（省 1 天）
5. **证据表 → 只留 3 条最强的**（省半天）

> **砍到第 5 项还缺时间，说明这个赛不该打，或者该换赛道。** 不要用"熬更多夜"去补结构性缺口。

### 一个容易忽略的分支：有没有预赛环节

| 赛制 | S2 的产出 |
|---|---|
| **有预赛**（报名 → 提交文档 → 入围 → 现场） | `docs/product/预赛材料.md`，按 §五 的硬指标写 |
| **无预赛**（报名 → 直接现场 24/48h） | **不写预赛文档。** S2 的产物并入 `docs/product/选题卡.md` 最后一栏"给谁看、为什么信"，1 页以内 |

**判据**：赛程里有没有"提交材料 → 等通知 → 入围"这一步。没有，就别花三天写九章文档——那三天应该换成预埋链路。

## 一、总览

> **下表是 L 档（P ≥ 25 天）的骨架。** 准备期更短时，先读 §零 选档，再回来按对应档位的日程走。表中 T 数字在短赛制里**没有对应日期**。

| 阶段 | 时间（L 档） | 一句话目标 | 产出物（落到哪） | 门 |
|---|---|---|---|---|
| **S-1 参赛决策** | T-30 ~ T-22 | 决定打不打、打哪个赛道、和谁打 | `docs/product/赛程卡.md`、`docs/product/赛道评估.md`、`flow/team.md` | — |
| **S0 逆向** | T-21 ~ T-14 | 算出这场比赛怎么赢 | `docs/product/逆向三表.md` | — |
| **S1 选题** | T-14 ~ T-10 | 收敛到 1 个题 | `docs/product/选题卡.md`、`docs/product/证据表.md` | **G1** |
| **S2 论证** | T-10 ~ T-5 | 证明值得做且做得到 | `docs/product/预赛材料.md`（**仅限有预赛**） | — |
| **S3 预埋** | T-5 ~ T-1 | 把七成做完 | 资源 + 链路 + `docs/architecture/契约冻结.md` + 部署环境 | **G2** |
| **S4 构建** | 0h ~ F 点 | 接上，不从零造 | live demo + 录屏 | **G3**（F 点） |
| **S5 交付** | F 点 ~ 提交 | 降低信任成本 | 六件套 | **G4** |
| **S6 沉淀** | 赛后 48h | 变成下次的资产 | 复盘帖 + 反哺清单 | — |

**每个阶段的产出都必须落文件。** 只在对话里说过的判断，等于没做过——下一棒读不到，评委也看不到。

### 先记住 O 点和 F 点

| 记号 | 含义 | 怎么算 |
|---|---|---|
| **O 点** | 比赛正式开始（拿到赛题那一刻） | 现场是开场，线上是赛题公布 |
| **F 点** | **功能冻结点** | **F = 提交截止时间 − 7 小时**，且不落在 22:00–06:00（落在此时段就前移到当天 22:00） |

> **"17:00" 不是墙上的下午 5 点，是"第 17 小时"。** 24 小时赛里，第 17 小时 = 提交前 7 小时 = F 点。很多人误以为是下午五点，结果 36 小时的比赛按 17:00 冻结，白白早了 20 小时。

## 二、S-1 参赛决策（L 档：T-30 ~ T-22）

**这一步决定你有没有资格谈"拿名次"。** 大部分人的失败在这一步就发生了：报了个不合适的赛，或者报完才开始想。

### 四个日期，抄下来贴在显眼处

| 日期 | 为什么关键 |
|---|---|
| 报名开始 | 有些赛分批次，早报能选赛道 |
| **报名截止** | **检查点 R，不是 T-0。** 没报名后面全废，但倒计时原点在**提交截止** |
| 提交截止 | 反推 F 点 |
| 评审 / 公布 | 决定你什么时候该发复盘帖 |

### 六件事，前两周定完（顺序不能反）

| 序 | 动作 | 时间 | 产出 | 判据 |
|---|---|---|---|---|
| 1 | **读输入 + 建容器（同一次对话）**：官网 / 赛道说明 / 群聊 / 实物，只抽"三个日期 + 赛道列表 + 必须用什么"；抽完立刻 `git init` 铺空壳 | **第 1 天**（T-30 或你看到链接的那天） | `docs/product/赛程卡.md` + 待问清单 + **可 clone 的空仓库** | 能一句话说清"这场怎么比"（时长 / 人数上限 / 线上线下 / 评审方式）；今天的调研有地方放 |
| 2 | **判主办方动机**（五型） | T-30 ~ T-27 | `docs/product/赛道盘点.md` 第一行 | 能说出"他们为什么办这个赛" |
| 3 | **定核心二人**：队长 + 主程 | T-25 | `flow/team.md` 前两行 | 这两人到位前，五维打分的"存量"项是失效的 |
| 4 | **盘点所有赛道**：先减法（三类直接删）→ 五维打分 → 每个赛道一句建议 | T-25 ~ T-22 | `docs/product/赛道盘点.md` | 有第一选择 + 备选，且备选写了**触发条件和切换成本** |
| 5 | **报名 + 打通一次上线** | **T-22 当天** | 报名成功截图 + 公网能打开的白页 | 报名别卡最后一天；白页用来暴露"发不出去"（域名/证书） |
| 6 | **按环节数补人** | T-22 ~ T-18 | `flow/team.md` 完整 | 六个职能无空缺，否决权归一人 |

详规：`13-输入解析与赛道盘点.md`（输入解析 / 动机五型 / 多赛道盘点 / 人数技能反推）+ `08-赛道与组队.md`（五维细则 / 赛制套利 / 组队契约）

> **铁律一：先报名，再准备。** 顺序反了会出现"准备了十天，发现名额满了"。
>
> **铁律二：容器在第 1 天建，代码在 T-5 写。** 这两件事差五周，不是三周。调研从第 1 天就开始，那时还没有仓库 → 产物只能留在聊天记录里，而群聊是搬运时丢得最多的地方。**"工程在前"指的是容器，不是代码。**（见 `SKILL.md`「工程分四层建」）
>
> **铁律三：容器只建"今天有东西要放"的目录。** 模块目录（`web/` `api/` `android/`）等 G1 定了形态再建——提前建等于赌自己会选 App。

## 三、S0 逆向（L 档：T-21 ~ T-14）

**只做一件事：搞清这场比赛的钱发在哪。**

### 先分级：评分表到手了吗

**评分表不是必然在赛前给你。** 它可能赛前到、开赛后到、路演前才到，或者始终不给。这一步决定 S0 做多少、什么时候收手。

| 形态 | S0 怎么做 | 什么时候收手 |
|---|---|---|
| **A** 赛前完整 | 全流程做，按权重排优先级 | 正常 |
| **B** 只有维度名 | 按等权假设做，**同时去要权重** | T-12 还没回，就按等权定下来 |
| **C/D/E** 没有 | 只做下面**不依赖评分表的那几项**（主办方 / 往届 / 资源） | T-14 硬收手，转 S1 |

**关键纪律：不知道评分表，S0 也必须走完。** 因为它只有一项依赖评分表，其余四项不依赖——而那四项恰好决定选题。

> 完整机制见 `12-评分表迟到.md`。核心结论：**把评分对齐当成会刷新的输入，不是一次性阶段**；成本随阶段上升（T-10 = 1x / 现场 = 10x），所以越早留锚点越好。

### 五项动作

| 动作 | 产出 | 依赖评分表？ | 判据 |
|---|---|---|---|
| 读赛题 10 遍，抄下每一个名词 | 赛题关键词表 | ❌ | 能背出主办方自己的说法 |
| 查主办方财报 / 官网 / 招聘 | 逆向表①：他们缺什么 | ❌ | 能说出"他们今年在押注什么" |
| 找往届获奖作品 | 逆向表②：评委见过什么 | ❌ | 能说出"什么样的稿子会被记住" |
| 数奖项结构 | 逆向表③：几个奖 / 谁竞争 | ⚠️ 部分（要权重才准） | 能算出"哪个格子的竞争者最少" |
| 摸资源清单 | 资源表：硬件 / SDK / 数据 / 专家 | ❌ | 能列出"主办方能给我什么别人拿不到的" |
| 抄评分细则（若有） | `docs/architecture/评分映射表.md` 第一段 | ✅ | 能逐项对上"我哪段内容服务它" |

**过这一段的标志**：你说得清"这场比赛的评分函数长什么样"；**或者说得清"我不知道评分函数，但我按哪套等权假设在推进"**。后者也算过——不知道自己不知道才不算过。

详规：`01-逆向工程.md`（§零 先确认评分表到手了吗）+ `12-评分表迟到.md`

## 四、S1 选题（L 档：T-14 ~ T-10）· G1

**三级收敛，不允许并行探索。**

```
市场（哪个区域，主办方投入大）
  → 人群（谁真的会付钱 / 谁会痛）
    → 痛点（最痛的那一个，且 24h 能演示）
```

| 动作 | 产出 | 注意 |
|---|---|---|
| 抓差评（Amazon / 独立站 / Reddit / 应用商店） | `docs/product/证据表.md` 前 10 条 | 只信差评，不信五星 |
| 抓竞品差评做对照 | 失败清单 | 竞品在哪摔的，你就在哪站住 |
| 列 5 个痛点，选 1 个 | `docs/product/选题卡.md` | 并列 3 个等于 0 个 |
| 算判据 | 选题卡"判据"栏 | 必须可算，不可感 |
| 定产品形态（App / Web / 硬件 / Agent） | 选题卡"形态"栏 | 没有界面的形态一律不选 |

### G1 过门检查

- [ ] 判据可算（写出算式或阈值）
- [ ] 有 ≥5 条差评原文（带链接与日期）
- [ ] 主办方能给不可替代的资源（写明是什么）
- [ ] 24h 内能演示出核心效果（写明怎么演）
- [ ] 产品形态已定，且**有可见界面**

**过不了就换题。** 不要"降低一点要求凑合过"，选题错了后面全部作废。

详规：`02-选题与调研.md`、`03-论证与预赛.md`

## 五、S2 论证（L 档：T-10 ~ T-5）· 仅限有预赛

> **先确认有没有预赛环节。** 赛程里没有"提交材料 → 等通知 → 入围"这一步，就**跳过本节**，S2 的产出压成 `docs/product/选题卡.md` 最后一栏"给谁看、为什么信"（1 页以内）。那三天应该换成预埋链路。

**预赛文档是这个阶段唯一交付物，它的真实身份是"预赛的目录结构"。**

九章骨架（详见 `03-论证与预赛.md`）：市场结构 → 目标细分 → 单户/单点经济性 → 竞争与增量 → 制度与迁移 → 商业进入 → 产品矩阵 → 推广价值 → 附录（来源 / 边界）。

| 硬指标 | 门槛 |
|---|---|
| 表格数 | ≥ 10 张（全是数据表，不要装饰图） |
| 来源 | 每条带"适用范围 / 读取边界" |
| 数字 | 每个标"不能用它证明什么" |
| 公式 | 关键结论要有算式，不要只有结论 |
| 功能清单 | 已按 P0/P1/P2 分档，P0 只有 1 个 |

**这一阶段最反直觉的动作**：主动删掉自己算出来的漂亮数字。评委见过太多"预计千亿市场"，**主动废除一个数字比增加十个更可信**。

详规：`03-论证与预赛.md`

## 六、S3 预埋（L 档：T-5 ~ T-1）· G2

**这五天决定现场能不能跑起来。** 四件事，按顺序：

### ① 拿资源（T-5 ~ T-4）
向主办方要硬件 / SDK / 真实工单 / 内部专家。

> 拿到 = 护城河 + "可落地"证据。没拿到 = 你的 demo 是想象出来的。

### ② 预埋链路（T-4 ~ T-3）
设备接入、鉴权、上传、模型调用——**全部跑通一遍**，记下每一步用了多久。

- 设备连不上就是 0 分
- 现场只换业务逻辑，不换链路
- 每条外部依赖准备一个降级方案，写进 `flow/assumptions.md`

### ③ 预埋部署（T-3 ~ T-2）
服务器、域名、HTTPS、安卓签名、iOS 证书、分发通道、演示机 —— **全部就绪**。

> 到现场才配的，每一件 1–2 小时且大概率失败。**iOS 证书配置 60–120 分钟，现场做等于弃赛。**

详规：`10-发布与部署.md`

### ④ 冻结契约（T-2 ~ T-1）· **G2**

| 冻结项 | 具体到什么程度 |
|---|---|
| 一页范围 | 固定场景、固定输入、**不做什么**（这一栏最容易被跳过） |
| 三条固定查询 | 不是十条，就三条，每条写清输入输出 |
| 版本化 JSON 样例 | 请求 + 返回，成功/空/错/无覆盖四份 |
| 核心 ID + 四类状态 | 成功 / 空结果 / 无覆盖 / 错误，各一份样例 |
| 字段命名与格式 | 命名风格、时间格式、ID 类型、空值表示、分页结构（五条一次性定死） |

产出 `docs/architecture/契约冻结.md`。

### G2 过门检查

- [ ] 一页范围写完，"不做"栏有内容
- [ ] 三条查询样例可直接拿去写代码
- [ ] 四类状态样例齐全（少一类，现场就会卡在那类）
- [ ] 依赖清单每条都有降级方案
- [ ] 部署环境已验证（公网能打开一个 hello）
- [ ] 模块目录已按形态建好（`web/` `api/` …，**不建用不到的**），每个模块有 `AGENTS.md` + `CLAUDE.md`，`scripts/dev.sh` 能起

## 七、S4 构建（O 点 → F 点）

### 时间分块（以 24h 为例，按比例缩放到 36/48h 见第十节）

| 时段 | 干什么 | 不许干什么 |
|---|---|---|
| 第 0–1 小时 | 开工对齐：读 charter / plan / 契约冻结，确认分工；确认提交方式与真实截止时间 | 不许直接写代码 |
| 第 1–6 小时 | 主链路打通（各人并行，用 fixtures 对接口，不等后端） | 不许做次要功能 |
| 第 6–9 小时 | 睡 / 轮换（至少 3 小时，写进计划） | 不许全队不睡 |
| 第 9–14 小时 | 补演示路径上的坑，加第二个功能 | 不许碰架构 |
| 第 14–F 点 | 端到端连跑 3 次 + 首次真实部署 | 不许改核心逻辑 |
| **F 点** | **G3 功能冻结**（拉 release 分支、打 tag） | **之后只修不加** |
| F 点 → 提交前 1h | 拍视频、录屏、写路演、做路演 HTML | — |
| 提交前 1h → 提交 | 交付门自检、彩排、提交 | 不许大改 |

- [ ] `flow/claims.md` 断言已在跑，不是"打算跑"

- [ ] 至少有一份录屏（现场翻车时的兜底）

## 八、S5 交付（F 点 → 提交）· G4

### 六件套

| 件 | 作用 | 常见错误 |
|---|---|---|
| live demo | 证明真做了 | 只在本地跑过，没在演示机上跑 |
| 录屏（2 分钟） | 兜底 + 给评委回看 | 最后 30 分钟才录 |
| 一页痛点证据 | 证明需求真实 | 全是二手转述 |
| 量化结果 | 证明有效 | 数字没来源 |
| 仓库 / 详情页 | 证明可复现 | README 里没有运行方式 |
| 复盘帖 | 加分（主办方最爱） | 赛后懒得写 |

### 路演三段式

**真实场景 → 可体验功能 → 三个核心设计 → 架构与边界**（5 分钟讲述 + 2 分钟问答）

不讲技术栈，讲"所以解决了谁的什么问题"。每个功能后面必须跟一句"为什么这样做"。

### F 点后第一件事：整仓整理（90 分钟，六步）

**不是提交前 30 分钟做**——第 4 步（新机器验证）一旦失败，修起来一小时起步。

| 序 | 步 | 产出 |
|---|---|---|
| 1 | **清** | 无密钥 / 无内网地址 / 无本地路径 / 无 `node_modules` `dist` / 无 >10MB 数据 |
| 2 | **正** | 命名统一、`example` 占位符清零 |
| 3 | **补** | README 四段 + `docs/architecture/项目结构.md` 七段 + LICENSE + `.env.example` + `.gitignore` |
| 4 | **验** | **clone 到干净目录，只照 README 敲，能跑到出结果** |
| 5 | **锁** | 打 tag `v1.0`，交付链接指向 tag |
| 6 | **点** | 无痕窗口 + 手机各点一遍所有链接 |

**顺序不能反**：先删才知道文档里哪些路径要改。
**这一步之后禁止改目录结构**，只做加法（补文档）和减法（删死代码）。

详规 + 打勾清单：`15-项目结构与提交整理.md` §六–§九

### G4 过门检查

用 `assets/materials/评分自检表.md` 打勾，**≥ 23/25 才允许交**；再用 `assets/materials/发布检查清单.md` 确认部署侧无遗漏；**外加一条硬门：干净目录 clone 后照 README 能跑起来**（跑不起来，前面全白做）。

**过不了**：放弃"能做全"，保"能演示 + 能讲清"。

详规：`06-叙事与交付.md`、`10-发布与部署.md`

## 十、时长适配：24 / 36 / 48 / 72 小时

**同一套流程，不同的压缩点。** 关键是 F 点跟着提交时间走。

| 时长 | 特点 | F 点 | 策略调整 |
|---|---|---|---|
| **24h** | 只够接上预留 | 提交前 7h | 标准流程。**不要试图加第二个功能** |
| **36h** | 多一个白天 | 提交前 7h | 主链路在第 12h 前必须通；多出的时间用于**补第二个功能 + 打磨演示**，不是加第三个 |
| **48h** | 接近小项目 | 提交前 8h | 第 24h 设一个"迷你 G3"（主链路通 + 断言跑），过不了就砍到 24h 方案 |
| **72h+** | 已是短项目 | 提交前 8h | 用 `project-flow` 完整骨架，本 skill 只作方法论参考 |

### 36h 的典型时间表（例：周六 10:00 → 周日 22:00）

| 时段 | 干什么 |
|---|---|
| 周六 10:00–11:00 | 对齐 + 确认提交方式 |
| 周六 11:00–18:00 | 主链路 |
| 周六 18:00–23:00 | 第二功能 / 补坑 |
| 周六 23:00–周日 03:00 | 轮换睡 4h |
| 周日 03:00–08:00 | 补坑 + 首次真实部署 |
| 周日 08:00–11:00 | 连跑 3 次 + 修稳定性 |
| **周日 15:00** | **F 点（22:00 − 7h）** 冻结、拉 release |
| 周日 15:00–19:00 | 视频 + 路演 HTML |
| 周日 19:00–21:00 | 彩排 + 自检 |
| 周日 21:00–22:00 | 提交（留 1 小时缓冲） |

### 48h 的坑

> **48 小时最容易出的问题不是时间不够，是"以为时间够"。**
> 签到时确认：`48h 的队通常在第 36 小时集体崩溃`。所以迷你 G3 必须设在第 24 小时，用它逼自己砍范围。

## 十一、准备期已过、比赛还没结束：只剩几小时怎么办

> **准备期分档（P ≥ 1 天）在 §零，不在这一节。** 这一节只管一件事：**现在已经在比赛里/今天就要交，来不及做任何前置动作。**

### 只有 24 小时（H=24，P=0）

| 小时 | 做什么 | 别做 |
|---|---|---|
| 0–1 | 逆向 + 选题同时做，1 小时内定死方向；**同时确认提交入口能打开** | 不要研究往届作品 |
| 1–2 | 写一页范围 + 三条查询（G2 压缩版，30 分钟） | 不要写架构文档 |
| 2–6 | 主链路 | 不要先做登录/注册 |
| 6–12 | 功能 + 断言 | 不要加第二个场景 |
| 12–15 | 轮换睡 | 不要通宵 |
| 15–F | 连跑 3 次 + 部署 + 冻结 | 不要在这个窗口改架构 |
| F–提交前 1h | 视频 + 路演 | 不要这时候补功能 |
| 最后 1h | 自检 + 彩排 + 提交 | 不要重录视频 |

**这种模式下，选题只能选主办方给了现成资源的那条**——没有时间验证需求，就借主办方的判断。

### 只剩 2–4 小时就要提交

**放弃做功能，只做四件事**：① 确认真实可访问的体验地址 ② 录 90 秒屏 ③ 写清"做了什么 / 没做什么" ④ 提交页每条链接点一遍。
**这四件事的收益高于任何一次代码提交。**


## 十二、时间轴的三条硬规则

1. **F 点冻结功能。** 之后只修不加。这一条违反率最高，也最致命。F 点要写在白板上，不是记在脑子里。
2. **视频和路演占 4 小时，写在计划里。** 不写进计划就一定会被开发吃掉。
3. **至少 3 小时睡眠，轮换。** 通宵的队在第 20 小时会做出比睡觉更糟的决定。

### 还有一条关于提交

4. **提交时间按主办方口头通知的，要再确认一次。** 宣传页、日程表、现场通知三者经常不一致，取**最早的**那个作为你的截止时间。
