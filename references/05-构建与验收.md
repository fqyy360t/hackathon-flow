# 05 · 构建与验收

> 目标：让"做完了"从一句自我感觉，变成一组可执行检查。
> 来源：`project-flow` 的 flow/docs 分层与五段循环 + 两个冠军仓库的工作包制与断言体系。

---

## 一、工作包制，不是里程碑制

| 维度 | 里程碑制（常见） | 工作包制（本 skill） |
|---|---|---|
| 结构 | 时间轴切片 | 依赖图，可并行 |
| 第一项 | 直接开工 | **D01 契约冻结** |
| 验收 | 全部做完才验 | 每包独立验收 |
| 状态 | 完成 / 未完成 | 代码已有 / 局部实测 / 完整验收 |
| 出问题 | 一起延期 | 只影响一个包 |

**为什么 24 小时必须用工作包制**：里程碑制里一个人卡住，全队等；工作包制里卡住的包可以降级交付，其他包照常。

---

## 二、D01 契约冻结（第一件事，不是最后一件事）

多数队伍把"定接口"放在开发中途，结果是每个人按自己理解写了三天，最后两小时对齐。

D01 只做四样，做完才允许并行：

| 冻结项 | 做到什么程度算冻结 |
|---|---|
| 一页范围 | 固定场景 + 固定输入 + **不做什么**（这栏必须非空） |
| 三条固定查询 | 每条写清输入、输出、边界；不是十条模糊的 |
| 版本化 JSON 样例 | 请求 + 返回各一份，字段名与类型确定 |
| 四类状态样例 | 成功 / 空结果 / 无覆盖 / 错误，各一份 |

**硬规则**：D01 未冻结，任何人不得开写业务代码。

**为什么是"四类状态"而不是"两类"**：现场最常翻车的是"空结果"和"无覆盖"——代码在成功路径上跑得很好，评委一问"如果一个都没有呢"，界面直接白屏。四类样例写好，这一栏永远不会白。

产物：`docs/architecture/契约冻结.md`

## 三、工作包卡：六个字段

`flow/tasks/D0X-<短描述>.md`

```markdown
# D03 · 事件查询与证据回查

- **主责**：<一个人名 + 目录>          ← 一个人，不是"前端组"
- **前置**：D01（契约冻结）
- **交付**：<可核对的具体物，不是"完成查询功能">
- **验收断言**：<C01 / C02 / C03 通过，见 flow/claims.md>
- **不做**：<明确排除的东西>            ← 防止范围膨胀
- **状态**：代码已有 / 局部实测 / 完整验收
```

### 「不做」这一栏为什么必须有

24 小时里最大的风险不是做不出来，是**范围自己长大**。

写"不做"的花费是 30 秒，能省下的是现场两小时的争论。写法示例：

> 不做：多摄像机关联、历史趋势、导出、权限分级、移动端适配

## 四、状态三分类（禁止写"已完成"）

| 状态 | 判定条件 |
|---|---|
| `代码已有` | 代码写完了，用假数据/样例跑过 |
| `局部实测` | 用真实数据跑过至少一次，结果可复现 |
| `完整验收` | 真实数据 + 断言全过 + 另一模型评审 PASS |

**为什么要分三类**：`代码已有` 和 `完整验收` 之间，藏着 80% 的工作量。

对照写法：

| ❌ 不要写 | ✅ 要写 |
|---|---|
| 已完成 | 代码已有实现，模拟数据通过，真实数据未验收 |
| 接口通了 | 样例接通，仅证明接口与交互可用 |
| 测试通过 | 42 项断言通过，真机未验 |
| agent 跑通了 | 计划生成成功，执行超时，尚无成功答复 |

**反直觉的价值**：一支冠军队伍在仓库 README 里明写"真实业务闭环仍未通过"。**评委不需要相信你，只需要相信你的记录。** 写清边界比宣称完成更可信。

## 五、断言清单：把验收写成能跑的

`flow/claims.md`。这是本 skill 相对 `project-flow` 最重要的一处加强——**原来的"验收标准"是给人看的，断言是给脚本跑的**。

### 每条断言的格式

```markdown
| ID | 断言 | 类型 | 怎么验 | 状态 |
|---|---|---|---|---|
| C01 | 输入固定查询，返回的事件 ID 都属于指定录像与区域 | 硬 | 脚本断言 | 待办 |
| C02 | 引用里的每个 ID 都在本轮返回结果中 | 硬 | 脚本断言 | 待办 |
| C03 | 空结果时返回空列表 + 明确提示，不报错、不白屏 | 硬 | 手工触发 | 待办 |
| C04 | 覆盖范围外时返回"无覆盖"，不与"零事件"混淆 | 硬 | 手工触发 | 待办 |
| C05 | 依赖不可用时降级，不伪造结果 | 硬 | 断网/关服务 | 待办 |
```

### 四类必写断言

| 类型 | 断言示例 | 为什么必须有 |
|---|---|---|
| **范围** | 结果全部落在给定范围/租户内 | 越界是最容易被追问的 |
| **引用** | 每个引用都真实存在于本轮返回 | 编造 ID 是最致命的 |
| **边界** | 空结果 / 无覆盖 / 错误，三态分明 | 现场必问 |
| **降级** | 外部依赖挂了，不假装成功 | 现场网络必挂 |

### 打分口径纪律

如果材料里要放通过率，必须写成：

> 62/74（83.8%）＝ 首轮硬性断言通过率；73/74（98.6%）＝ 修复后单轮复测通过率。

**不能改写成"问题解决率从 83% 提升到 98%"**——分母不同、条件不同，一算就穿。

## 六、双门评审

`project-flow` 的评审是"换模型看"，这是对的一半。黑客松还要加一半：**脚本跑**。

| 门 | 谁执行 | 判什么 | 结果 |
|---|---|---|---|
| **断言门** | 脚本 | 事实对不对 | 通过率 |
| **评审门** | 另一个模型 | 讲不讲得通、有没有漏 | PASS / FAIL + 理由 |

两门都过 → 状态升到 `完整验收`。

### 评审门的提问模板

直接发给另一个模型，不要问"你觉得怎么样"：

```
你在评审一个黑客松项目。只回答三件事：
1. 哪个功能你无法从材料里确认它真的做了？（指出具体位置）
2. 哪个数字没有来源或边界说明？
3. 如果我是评委，我会追问什么？
不要给建议，只列问题。
```

**问"会追问什么"比问"有什么问题"有效**——它直接产出你要准备的答案。

## 七、假设台账：把"我不知道"变成合法状态

`flow/assumptions.md`。四级置信度，每条必须能回答"官方包下来，我改哪一个文件"。

| 标记 | 门槛 | 纪律 |
|---|---|---|
| ✅ 实证 | 官方源码 / 文档，可引行号 | 直接进代码与契约 |
| 🟡 强推测 | 有同源旁证 | 可进代码，**必留替换点** |
| 🟠 弱推测 | 仅类比惯例 | **不进契约** |
| ⬜ 未知 | 无依据 | **不写死，只进台账** |

**判据**：官方包下载下来，改哪一个文件能实现这个功能？答不上来 → 说明这是 🟠 或 ⬜，别写成 ✅。

这一条的价值在开局：黑客松处处未知，**它让"我不知道"变成可追踪的状态，而不是逼 agent 编一个像样的答案**。防止在假接口上写 6 小时代码。

## 八、24 小时协作纪律

### 目录与文件

| 情况 | 规则 |
|---|---|
| 多人改同一文件 | 串行整合，不并行 |
| 各自模块 | 独立目录，边界写进工作包卡的"主责" |
| 共享契约 | 只读，改要走 `flow/decisions.md` |
| 临时脚本 | 不进主目录，放 `scripts/tmp/` |

### 分支（如果用了 git）

```
main        稳定基线（现场基本不动）
dev         集成
feat/D0X-*  单包分支
```

**24 小时里，如果 push 一次要 40 分钟，就不要用分支协作，改同机开发。** 工具链要按真实成本算，不是按最佳实践。

### 每 3 小时一次同步

不写文档的同步等于没同步。每次同步只确认三件事：
1. 各包状态（三分类）
2. 有没有包卡住了（需要降级吗）
3. 演示路径还完整吗

## 九、这份东西在 24 小时里的最小集

| 保留 | 砍掉 |
|---|---|
| D01 契约冻结（压到 1 小时） | 完整 12 表 104 字段级契约管理 |
| 工作包卡六字段 | 完整任务卡流程与归档 |
| 断言清单 5–8 条 | 完整 benchmark + 红队三角色 |
| 状态三分类 | 完整评审历史归档 |
| 假设台账（只记 🟠⬜） | 四级全量记录 |
| 换模型评审一次 | 多轮评审与回归 |

**判断标准**：这条机制能不能在 30 分钟内落地？不能就降级或砍掉。**宁可少一条机制，不要留一条半成品。**
