# 03 · 论证与预赛：把方案写到站得住

> 目标：把"痛点"翻译成"结构化任务"，再把它压进 24 小时。
> 判据：任何功能，说不清"做什么/怎么做/为什么这样做"就不要写进文档。

---

## 一、方案的一句话检验

> 我的方案把 ___ 从 ___ 变成 ___。

- 填不出来 → 方案还没成形，回去做 S1。
- 填出来但是"把 XX 从手动变成 AI" → 太虚，AI 不是差异点，**任务结构**才是。

强样本（安防冠军队）：
> 把"用户自己翻事件判断"变成"摄像头替用户维护任务状态并给出有证据的结果"。
> 从 `运动检测 → 推送 → 用户打开录像 → 用户自己判断`
> 到 `用户定义关心的事 → AI 持续观察 → 维护任务状态 → 证据不足进入 UNKNOWN → 证据充分后确认 → 直接给结果`。

---

## 二、把需求编译成任务（最值得抄的一个设计）

用户说一句话 + 圈一个区域，系统生成**结构化任务**，字段固定：

| 字段 | 作用 |
|---|---|
| 观察对象 | 看什么（箱体 / 人 / 宠物 / 车辆） |
| 关注区域 | 在哪看（用户圈选） |
| 触发条件 | 什么时候开始判定 |
| 完成条件 | 怎样算达成 |
| **UNKNOWN 条件** | 什么情况下**必须承认判断不了**（遮挡、离线、过期画面） |
| 证据要求 | 结论必须附什么（关键帧 + 时间 + 来源设备） |
| 可调用设备与通知方式 | 谁来执行、怎么告知 |

**为什么这个设计强**：
- 它把"AI 能力"变成了"可执行、可验证、可复用的任务"；
- `UNKNOWN 条件` 是信任的根 —— 系统会说"不知道"，评委立刻相信它不会瞎编；
- 同一套 Runtime 换目标/区域/规则就能复用到第二个场景 → **复用性**直接对上"落地可行性"。

**通用化**：任何 AI 方案都可以套这个结构 —— 观察什么、在哪、触发、完成、**什么情况下不判断**、凭什么证明、谁来执行。

## 三、卡诺分档（功能取舍的唯一标准）

| 档 | 定义 | 24h 策略 |
|---|---|---|
| 基础型 | 没有就不可用 | 必须做，做到不出错 |
| 期望型 | 越多越满意 | **只做 1 个**，做成 demo 高光 |
| 兴奋型 | 用户没想到 | 只画一张图 / 一句话愿景 |

对照：赛道冠军做的是"引流产品"（单点做到极致），金点子奖做的是"品牌产品"（愿景级重构），**两者都不做利润产品**。这就是为什么"什么都做"的队赢不了。

## 四、产品形态与功能清单

### 4.1 产品形态四选一（这一选决定后面 24 小时的一切）

| 形态 | 24h 可行性 | 演示效果 | 前提 | 适合 |
|---|---|---|---|---|
| **Web 应用** | 高 | 中（依赖大屏/投屏） | 有网 | 工具、后台、B 端 |
| **手机 App** | 中 | 高（手持演示 + 投屏） | 队里有移动端的人 | 消费级、现场移动场景 |
| **硬件 + App** | 低 | **最高** | **主办方给硬件** | 有硬件资源时唯一正解 |
| **纯 Agent / API** | 最高 | **最低（看不见）** | 无 | ❌ 必须配可视化壳 |

**三条铁律**：

1. **没有界面的形态不要选。** 纯后端 / Agent 项目必须配一个最简壳（哪怕一个聊天框），否则 5 分钟里无法证明它存在。
2. **硬件形态只在主办方给硬件时选。** 自己买硬件 = 赛前三天在等快递，且拿到手只剩 2 小时调试。
3. **形态决定分工。** 选 App 就必须有移动端的人；选 Web 可以一个人全包。**先看队里有谁，再定形态。**

**先看品类，再看形态——形态不是自由发挥**

上面的四选一只是"技术载体"。真正决定形态的是**这个品类在市面上已经长成什么样了**。评委看到的第一秒是在归类，不是在欣赏：归不进任何一类，你就得多花两分钟解释，而路演只有五分钟。

| 品类（用户会怎么称呼它） | 市面主流形态 | 为什么是这个形态 | 24h 能砍到多小 |
|---|---|---|---|
| 效率工具 | Web / 浏览器插件 | 在电脑上干活，不想装 App | 一个页面 + 一个核心动作 |
| 消费级服务 | 手机 App / 小程序 | 随手用、要通知 | 3 页：首页 / 核心 / 结果 |
| 内容 / 社区 | 手机 App | 消费场景决定 | 信息流 + 详情 |
| B 端 / 管理 | Web 后台 | 桌面、大屏、表格 | 一个看板 + 一张表 |
| 硬件配套 | App + 硬件 | 必须有一端连物理世界 | 一个连接页 + 一个控制页 |
| 数据 / 分析 | Web + 图表 | 屏幕越大越好 | 一张图 + 一句结论 |
| Agent / 助手 | 聊天框 / 嵌入既有工具 | 用户不想学新界面 | 一个对话框 + 一条链路 |

**为什么"照着市场形态做"比"形态创新"划算：** ① 评委 5 秒内知道这是什么，认知成本为 0；② 演示路径是观众熟悉的，不用教评委怎么操作；③ 骨架可以照成熟产品抄，省掉设计时间。

> **在黑客松里，形态创新是负资产。** 你把时间花在"解释这是什么"，评委在算"这能不能用"。

**从品类反推功能——不是从想法反推**

品类定了，功能其实也大体定了。**把"我要做什么功能"改成"这个品类的标准功能清单里，我留哪三个"**：

1. 搜 3 个同类产品（应用商店页 / 官网功能页 / 截图），把它们的标准功能列出来
2. 划掉"这品类通常有、但我不做"的——**要能答"为什么不做也不影响演示"**
3. 剩下的按 P0 / P1 / P2 分档（§4.2）

> §4.3 讲的是**差异化从哪来**（差评 / 竞品失败点）；这里讲的是**底座从哪来**（品类标准清单）。
> **先有底座，再谈差异。没有底座的功能组合，看起来不是创新，是残缺。**

### 4.2 功能清单分三档，不是一张清单

| 档 | 数量 | 定义 | 24h 策略 | 怎么判断它在哪档 |
|---|---|---|---|---|
| **P0 引流** | **1 个** | 能 10 秒演完、一句话说清的核心动作 | 必须做完，且必须稳定 | 说不清"10 秒怎么演" → 还不是 P0 |
| **P1 支撑** | 2–3 个 | 让 P0 成立的必要环节 | 做完 1–2 个，其余降级 | 缺了它 P0 就不成立 → P1 |
| **P2 愿景** | 不限 | 说明方向，不做 | 只进架构图，demo 里说"下一步" | 删掉不影响演示 → P2 |

> **P0 只能有一个。** 两个 P0 = 两个都不突出 = 评委记不住。这也是"五个痛点是自杀"的工程版本。

与卡诺分档的对应：**P0 ≈ 期望型里最能演的那个，P1 ≈ 基础型，P2 ≈ 兴奋型。**

### 4.3 功能从哪来（三个来源，按可靠性排序）

| 排序 | 来源 | 怎么用 |
|---|---|---|
| 1 | **差评里的重复抱怨** | 出现 ≥3 次的抱怨直接变成功能 |
| 2 | **竞品的失败点** | 变成"我们在这站住"的差异点 |
| 3 | 团队自己的想法 | **必须能被前两条之一支撑**，否则不做 |

**过滤规则**：一个功能如果既不对应差评、也不对应竞品失败点，就砍掉。24 小时里没有"顺便做一下"。

### 4.4 功能卡（每个 P0 / P1 填一行）

| 功能 | 档 | 对应证据 | 10 秒怎么演 | 失败时怎么兜 | 不做会怎样 |
|---|---|---|---|---|---|

最后一列是自检：**"不做会怎样"如果只能答"也没什么"，就删掉它。**

## 五、AI 反向提问法（30 分钟把模糊想法逼具体）

不要问 AI "帮我设计方案"，而是自建一个"需求澄清助手"，让它**反过来问你 20 轮**：

```
你是资深产品评审。我的赛题是【___】，我的初步想法是【___】。
请不要给方案，只做一件事：连续问我 20 个问题，把我模糊的地方逼到必须给出具体答案。
每轮只问 1 个，等我回答后再问下一个。问题要覆盖：谁、什么场景、现在怎么解决、为什么现有方案不行、什么条件下我的方案会失效。
```

问完把答案填进「预赛材料模板」的第 1、3、8 节。

## 六、从经营目标反推，流程放最后

### 6.1 六要素，从经营目标反推

```
经营目标 → 问题/角色/数据/证据/权限/流程 → 五阶段闭环 → 工具与 Agent
```

| 要素 | 要定什么 |
|---|---|
| 问题 | 一句话，可验收 |
| 角色 | 谁用、谁决定、谁付钱、谁授权 |
| 数据 | **来源与质量优先**：来源 / 采集时间 / 可信度等级 / 可追溯凭据 |
| 证据 | **留下验证记录**：每条结论附凭据（工单号、差评原文、日志片段） |
| 权限 | 谁可以改、可以看、可以停 |
| 流程 | **永远放最后**：流程是从上面五项长出来的，不是先定流程再找事做 |

顺序反了（先让 AI 搭一个再想交付给谁），做出来的东西没有交付对象。

> 角色怎么拆成五类（使用者 / 受益者 / 付费者 / 决策者 / 授权者）、条件怎么分组、四层漏斗怎么逐层判，见 `02` §一·补。**先有经营目标和角色，再定流程**——流程是从上面五项长出来的，不是先定流程再找事做。

### 6.2 五阶段闭环（loop，不是流水线）

```
观察 → 判断 → 行动 → 验证 → 修正 →（回到观察）
```
每轮必须留下：**做了什么 / 依据是什么 / 结果如何 / 下一轮改什么**。
6.3 置信度四级 → 见 `assets/flow/assumptions.md`
6.4 仓库契约与多 Agent 协作 → 见 `07-协作机制.md`
6.5 完成定义（三级验证）→ 见 `05-构建与验收.md`

## 七、指标反作弊（每人必须能回答）

| 真指标 | 不能替代它的东西 |
|---|---|
| 数据完整性（有效时点比例） | 日志条数 |
| 计算正确性（能量守恒、独立求解核对） | 同一代码重复运行 |
| 执行确认（已确认 / 失败 / 未知比例） | HTTP 成功率 |
| 使用理解（答对任务比例） | 点击率、追问次数 |
| 商业结果（实际付款、续用） | 注册数、市场份额 |

**用法**：任何人说"跑通了"，追问一句"是这六个里的哪一个？"

## 八、兜底

- 核心技术路线 **拿到真机后 2 小时内重验**，超时立刻切降级方案。
- 每个 demo 路径准备一条"保险丝"：录屏 / 本地 mock / 预置数据，但**主路径必须真跑**。

## 九、写成可重排的模块（评分表迟到时的唯一保险）

**问题**：评分表可能赛前不给、赛中才给、甚至不给。如果预赛文档是"一条从头串到尾的线性论证"，评分表一到你只能重写。

**解法**：按**可独立摘出的模块**写。

| 写法 | 评分表迟到时 | 判断 |
|---|---|---|
| 线性论证：第 1 节为第 2 节铺垫，第 3 节引用第 2 节结论 | 改任何一处都要改三处 | ❌ |
| 模块化：每节自带前提、自身成立、可单独发给别人看懂 | 重排顺序、砍掉一节，都不影响其它 | ✅ |

### 模块化的三条硬要求

1. **每节开头一句话自证**："这一节证明 ___"。让读者从任意一节开始都能接上。
2. **一个功能一张卡**，卡头写「服务评分项：___」。打乱卡片顺序，故事仍然成立。
3. **跨节引用改成重复一句**，不要写"如上所述"。重复 20 字换取可重排，很划算。

**判据（当场可验）**：任取一节，单独发给没看过全文的人，他能不能看懂？看不懂就是没模块化。

> 为什么值得做：赛中拿到评分表时，**所有人的材料都要重切**。模块化 + 评分映射表 = 30 分钟重排；线性长文 = 3 小时重写，直接挤占 demo 与彩排时间。详见 `12-评分表迟到.md` 第七、十节。

## 十、赛后复盘要写什么

> **完整做法在 `16-赛后复盘与资产化.md`**（四层：事实 → 归因 → 可复用 → 反哺；归因要分清"判断错"和"执行差"）。这里只留速查五条。

- 实际做了什么 vs 文档里只是建议的（分开写，别把建议包装成已实现）
- 哪个判断在中途被推翻，为什么
- 哪一步最耗时，下次怎么砍
- **评分表什么时候到的、重对齐花了多久、迟到损失了什么**（这条用来校准下一场的判断）
- 保留的反例与不同意见（不要只写成功路径）

**判据**：这次复盘能不能让下一场的 T-21 少花两天？
