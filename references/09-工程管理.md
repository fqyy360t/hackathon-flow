# 09 · 工程管理：一个控制面，多个模块

> **结构继承 `project-flow`**：一个总体项目只有一个控制面（根级 `flow/` + `docs/`），每个子项目一个局部入口（`AGENTS.md` + `CLAUDE.md` 软链），不重复建控制层。
> 前提：**这是比赛，不是长期项目。所有工程手段的判据只有一条——能不能减少现场的等待时间。**

---

## 零、目录生长表：第几步建到哪一层

**这一节回答"工程框架是不是第 1 步就生成"。答案是：容器第 1 天就建，但不是一次建完——分四次生长。**

| 时点 | 建什么 | 建到第几层 | 为什么是这个时点 |
|---|---|---|---|
| **第 1 天**（拿到比赛链接的同一次对话，30 分钟） | `git init` + `AGENTS.md` + `CLAUDE.md` 软链 + `flow/`（空模板）+ `docs/` 五个子目录 + `.hooks/`；**（用户要的话）远程仓库 + 首次 push** | **只建"今天就有东西要放"的目录**，一个模块目录都不建 | **调研从第 1 天就开始，产物必须有落点。** 晚一天 = 那天查到的差评、竞品、访谈进聊天记录，到 T-22 搬运时丢一半 |
| **T-22**（选完赛道，1 小时） | CI 骨架 + 一个能打开的部署白页 + 域名/证书预验 | 部署链路打穿一次 | 白页的作用是**提前暴露"发不出去"**（域名备案 / iOS 证书 60–120min），不是装资料 |
| **G1 通过（T-10）** | 按产品形态建**模块目录**，每个模块配 `AGENTS.md` + `CLAUDE.md` | `web/` `api/` 或 `android/` `ml/`，**形态说几个就建几个** | 形态是 G1 定的，目录是形态的影子 |
| **S3（T-5 ~ T-3）** | 技术选型、脚手架、`docs/contracts/`、`infra/`、`scripts/` | 模块内部任意深 | 选型跟着选题走，早选必废 |
| **F 点** | `release` 分支 + tag `v1.0` | **不再新增目录** | 只修不加 |

**三条判据：**

1. **第 1 天建容器不建代码。** 空目录 + `.gitkeep`，只为了让资料有地方放。**判据是"这个目录今天有没有东西要放进去"**——有就建，没有就等到有。
2. **模块目录在 G1 之后建。** G1 之前建 `android/`，等于赌自己会选 App；没选就剩一个空文件夹，评委会看见。
3. **模块内部结构在 S3 建。** 脚手架是选型的产物，选型是选题的产物。

> **反模式一：T-22 就把 `web/ android/ ios/ api/ ml/` 全建好。** 最后四个是空的，git 里一片 `.gitkeep`。这不会加分，只会让评委觉得你不知道要做什么。
>
> **反模式二：等选完赛道再建仓库。** 从拿到链接到 T-22 通常有 5–10 天，这段时间正好是调研最密集的时候。没有容器，产物只能落在聊天记录和本地文件夹里——**而这些恰好是 T-22 搬运时丢得最多的两处**（群聊里的口径一旦滚过去就找不回来）。
>
> **反模式三：第 1 天就把 CI、脚手架、五个模块目录全铺好。** 这叫"工程先行"的错版本：为了显得专业，先搭一个用不上的架子。T-5 真开始写时，一半要拆。

### 第 1 天那 30 分钟具体做什么

| 时段 | 动作 | 落点 |
|---|---|---|
| 0–5 min | 抽三个日期（报名截止 / 提交截止 / O 点）+ 拉赛道总表 | `docs/product/赛程卡.md`（草案，可以有 ⬜未知） |
| 5–10 min | 判主办方动机五型（见 `13`） | `docs/product/赛道盘点.md` 第一行 |
| 10–20 min | `git init` + 铺 `flow/` `docs/` 空壳 + `AGENTS.md` + `.gitattributes` + 装 git 钩子 + 第一条 commit；（要远程的话）建仓库并 push —— 公开/私有见 `14` | commit + 可 clone 的远程仓库 |
| 20–30 min | 列七个待问清单发给用户 | `flow/decisions.md` 或直接对话 |

**结束时手上应该有**：一个空仓库（有 commit）、一份填了三个日期的赛程卡、一份只写了一行结论的赛道盘点、一张待问清单。**不是"整个目录结构"，是"资料能落的那几层"。**

**为什么第 1 天就装钩子和 `.gitattributes`**（10 秒的成本）：

- `.gitattributes` 管换行符。**晚了就来不及**——已经进库的 CRLF 脚本不会自己变回去，而 `pre-push` 变成 CRLF 会让钩子静默失效（`\r: command not found`）
- `pre-push` 钩子拦直推 `main`（`14` §四）。第 1 天只有你一个人，看似没用；**它的价值在于第 3 天第二个进仓库的人不会养成直推的习惯**
- 一条命令装完：`sh scripts/install-hooks.sh`（幂等，新队友 clone 后各跑一次）

## 一、目录结构：模块名做目录名，不按"前/后端"分层

### 最终形态

```
<项目>/
├── AGENTS.md                     根级运行时合同（唯一）
├── CLAUDE.md -> AGENTS.md        两个工具读同一份
│
├── flow/                         ★ 唯一控制层（推进项目）
│   ├── charter.md  team.md  未认领.md
│   ├── plan.md  claims.md  assumptions.md
│   ├── 进展.md  decisions.md  踩坑记录.md
│   ├── tasks/D0X-*.md
│   └── 规范/                     本 skill references 副本（自包含，赛后可复用）
│
├── docs/                         ★ 集中内容层（评委读、下一个人读）
│   ├── README.md                 索引，必须存在
│   ├── product/                  赛程卡 赛道盘点 产品与功能清单 证据表 预赛材料
│   ├── architecture/             项目结构 评分映射表 契约冻结说明
│   ├── contracts/                ★ 接口真相源（见 §二）
│   │   ├── api.yaml
│   │   ├── 字段命名.md
│   │   └── fixtures/             success / empty / error / no_coverage
│   ├── modules/<模块>/           只影响某一个模块的说明
│   └── reviews/                  跨模型评审记录
│
├── web/                          ┐
├── android/                      │ 每个模块独立一个目录，
├── ios/                          │ 每个目录一份 AGENTS.md + CLAUDE.md 软链
├── api/                          │ 按形态建，不是全建
├── ml/                           ┘ 离线部分，不进部署
│
├── infra/                        docker-compose.yml  Caddyfile  deploy.sh
├── scripts/                      dev.sh  check.sh  build.sh
└── .hooks/  .claude/  .codex/    只装在项目根
```

### 为什么是"模块名"而不是 `frontend/` `backend/`

`project-flow` 的默认例子是 `frontend/ backend/ landing/`，但它的原则是**一个模块一个目录、模块名就是目录名**，不是"必须叫前/后端"。黑客松的模块划分和长期项目不一样：

| 分法 | 加了安卓 iOS 之后 | 结论 |
|---|---|---|
| `frontend/` `backend/` | 变成 `frontend-android` `frontend-ios`，越加越乱 | ❌ |
| **`web/` `android/` `ios/` `api/` `ml/`** | 加一个端 = 加一个目录，其余不动 | ✅ |

**判据：新增一个端（鸿蒙、小程序、微信），要不要改现有目录名？** 不用改 → 结构对了。

> 这不是偏离 `project-flow`，是它的原则在"多端 + 48 小时"场景下的实例化。**原则是"一个模块一个目录 + 局部入口 + 唯一控制面"，目录名是例子。**

### 一个模块一个局部入口

```
web/
├── AGENTS.md        本模块职责 + 怎么跑 + 不许做什么（用 assets/MODULE_AGENTS.md 生成）
├── CLAUDE.md        指向 AGENTS.md（Windows 上复制，不做软链）
└── <源码、测试、构建配置>
```

模块级 `AGENTS.md` **只写三件事**：本模块负责什么 / 怎么跑起来 / 不许做什么。然后指回根级。

**不写**：总体目标、计划、任务卡、决策、交接。这些只进根级 `flow/`。

### 根级 `docs/` 五分法

| 目录 | 放什么 | 判据 |
|---|---|---|
| `product/` | 赛程卡、赛道盘点、产品与功能清单、证据表、预赛材料 | 回答"我们要做什么、为什么" |
| `architecture/` | 项目结构、评分映射表、契约冻结说明 | 回答"怎么搭、怎么对上评分" |
| **`contracts/`** | 接口定义、字段命名表、四类状态样例 | **跨模块的唯一真相源** |
| `modules/<模块>/` | 只描述某一个模块、但仍需统一发现的说明 | 不跨模块 |
| `reviews/` | 跨模型评审记录（PASS / FAIL + 理由） | 留证据，不是留意见 |

**代码邻近文档的例外**（不为了"集中"而搬家）：已有的 `README.md`、随代码生成的 API 文档、必须和代码同一次变更维护的开发说明。**在 `docs/README.md` 加一条索引即可。**

### `flow/规范/` 为什么要有

把本 skill 的 `references/` 复制进去。理由：**现场断网、换 Agent、换模型时，规则还在仓库里。** 这是 `project-flow`"详规随项目"的直接继承。

比赛版只复制**当前阶段要用的 3–4 份**，不全量复制（见 `SKILL.md` 边界）。

## 二、接口对齐：契约先于代码，且只有一份

**这是多端项目里唯一真正会拖垮进度的问题。** 前端等后端、安卓等接口、iOS 猜字段——全部源于"接口在两个人脑子里"。

### 三种做法的成本对比

| 做法 | 首次成本 | 改一次的成本 | 24h 适用性 |
|---|---|---|---|
| 口头约定 / 微信对齐 | 0 | 高（要重新对齐所有人） | ❌ 改两次就崩 |
| 手写 JSON 样例放进 `docs/contracts/fixtures/` | **10 分钟** | 低（改一处） | ✅ **推荐** |
| OpenAPI 全量 + 代码生成 | 1–2 小时 | 最低 | ⚠️ 有 Web 前端时值得 |
| protobuf / gRPC | 3 小时+ | 低 | ❌ 比赛不要用 |

### 24h 版最小契约（做这四件事就够）

1. `docs/contracts/api.yaml`（或 `types.ts`）——**只写这次 demo 用到的 6–8 个接口**
2. `docs/contracts/fixtures/` 下每个接口四份 JSON：`success.json` / `empty.json` / `error.json` / `no_coverage.json`
3. `docs/contracts/字段命名.md`——命名风格、时间格式、ID 类型、空值、分页，一次定死
4. 每份样例带 `_meta`：`{"_meta": {"owner": "甲", "updated": "10-27 03:20"}}`

**关键动作：前端和移动端在接口没实现前，直接读 `docs/contracts/fixtures/` 开发。** 这一条能把"等后端"的时间清零。

> **真相源只有一个，在 `docs/contracts/`。** 代码里如果需要 import 类型或 client，从它生成到 `shared/`，**不在 `shared/` 里二次定义**。两份定义必然漂移，而漂移是在第 18 小时发现的。

### 字段命名的一次性决定（省掉后面所有争吵）

| 决定 | 选一个 | 不选的代价 |
|---|---|---|
| 命名风格 | `snake_case`（后端友好）或 `camelCase`（前端友好） | 每端各写一层转换，且容易漏 |
| 时间格式 | **一律 ISO 8601 UTC 带时区**，如 `2026-10-27T03:20:00Z` | 时区 bug 在凌晨三点最难查 |
| ID 类型 | 一律 `string`（不用 int） | 前端 `Long` 精度丢失、跨语言不兼容 |
| 空值 | 一律 `null`，不用 `""` 或 `-1` | 三端判断逻辑不一致 |
| 分页 | 一律 `{items, total, cursor}` | 每端自己发明 |

**这一张表值得在开工第一小时花 10 分钟定死，写进 `docs/architecture/契约冻结.md`。**

## 三、环境统一：三条命令，五分钟能跑起来

```bash
scripts/dev.sh      # 起本地全套（后端 + 前端 + 依赖服务）
scripts/check.sh    # 跑 flow/claims.md 的断言
scripts/build.sh    # 打出可演示的产物（apk / ipa / dist）
```

### 判据

> **一个新队友 clone 下来，5 分钟内能跑起来。** 做不到，就说明环境没统一——而现场补环境平均要 2 小时。

### 环境清单（赛前全部做完）

| 项 | 赛前要做的 | 现场才做的后果 |
|---|---|---|
| 依赖包 | `npm install` / `pip download` / gradle 缓存 / cocoapods 预拉 | 会场网络慢，装依赖耗 1–3 小时 |
| 镜像源 | npm / pip / gradle 换国内源，写进 `.npmrc` `.pip/pip.conf` | 默认源超时 |
| 运行时 | Node / Python / JDK / Xcode / Android SDK 版本写死在 README | 版本不一致，本地能跑现场不能 |
| 密钥 | **全部提前申请**：大模型 API、地图、云存储、推送 | 现场申请要审批，且可能要企业认证 |
| `.env` | 提供 `.env.example`，缺 key 时能降级跑 mock | 一个人没配 key，阻塞全队 |

### 密钥管理的三条纪律

1. `.env` 进 `.gitignore`，仓库里只有 `.env.example`
2. 密钥所有权写清：`docs/product/密钥清单.md`（谁申请的 / 有效期 / 额度 / 谁能用）
3. **赛前 48 小时测试一次额度**——很多免费额度不够跑完 24 小时的 demo

## 四、算法 / 模型这条线的特殊处理

算法是最容易拖垮进度的一环，因为它天然不可控。三条硬规则：

| 规则 | 做法 |
|---|---|
| **先有假接口，再有模型** | `api/` 第一天就提供 `/predict` 返回 mock 结果，前端不等 `ml/` |
| **模型与业务解耦** | `ml/` 只吃"文本/图片 → JSON"，业务逻辑不写进推理代码 |
| **准备降级链** | `真实模型 → 小模型 → 规则 → 预生成结果`，三级都要能返回结构合法的结果 |

### 常被问到的两个坑

- **推理延迟**：24h 项目不要上大模型做实时推理，一次 8 秒会让 demo 卡死。用"预生成 + 缓存"演。
- **权重文件**：几百 MB 的权重**不要进 git**，放对象存储，`scripts/dev.sh` 里做存在性检查。

## 五、版本与分支：24 小时里越简单越好

| 团队规模 | 做法 | 理由 |
|---|---|---|
| 1–3 人、同机开发 | **主干直推**，小步提交 | 分支合并的时间比冲突本身更贵 |
| 4 人以上、模块清晰 | `feat/<模块>` 分支 + 直接合并（不强制 PR review） | 保留回滚能力，不阻塞 |
| 任何情况 | **不要 rebase、不要改历史、不要 force push** | 凌晨改历史 = 丢别人的活 |

### 冻结期规则（和 G3 同一条）

```
F 点（提交前 7h）  →  从主干拉 release 分支，打 tag v1.0
F 点之后           →  只往 release 打补丁，主干不再合
提交前 1h          →  打 tag v1.0-final，构建产物定版
```

**演示用的是 `v1.0-final` 的产物，不是最新代码。** 很多人最后一小时还在改代码，结果演示的是没验证过的版本。

### 提交信息的最小规范

```
feat(api): 加 /predict 接口          ← 别人能看懂改了什么
fix(android): 修白屏
chore: 预装依赖
```

不需要复杂，只需要**让另一个人在 `git log` 里能定位**。

## 六、依赖与构建：按"真实耗时"排序

24 小时里最容易被低估的不是写代码，是**等**。把等待项按耗时排序，提前做完：

| 等待项 | 典型耗时 | 提前做的方式 |
|---|---|---|
| 依赖安装（首次） | 20–90 min | 赛前 `install` 一遍并提交 lock 文件 |
| Android 首次构建 | 15–40 min | 赛前跑一次 `assembleDebug`，gradle 缓存本地留着 |
| iOS 证书配置 | 60–120 min | **必须赛前做**，现场配证书等于弃赛 |
| Docker 镜像拉取 | 10–30 min | 赛前 `docker pull` 好，镜像别现场拉 |
| 大模型首次调用（冷启动） | 5–20 s | 提前 warm up，别在演示时第一次调 |

**判据：把"第一次"全部挪到赛前。** 现场只做"第二次"，第二次是快的。

## 七、代码质量的最低线（不要更多）

比赛不是写生产代码，但有三样不能省，因为**评委会看仓库**：

1. **能跑**：README 里的命令照着敲能启动（自己照抄一遍验证）
2. **能读**：关键函数有一句注释说明"这一步为什么这么做"（不是解释语法）
3. **不泄露**：密钥、内网地址、真实用户数据不能进仓库

**不要做的**：单元测试覆盖率、CI 流水线、代码规范全量 lint、类型全覆盖。这些在 24 小时里是纯消耗，收益体现在"看起来很专业"，而评委不看这个。

**唯一例外**：`scripts/check.sh` 背后的断言脚本必须写——它不是测试，它是**你的验收证据**（见 05）。

## 八、多端并行时的冲突热点

| 热点 | 为什么会冲突 | 预防 |
|---|---|---|
| `docs/contracts/` | 谁都想改字段 | **只有一个人有写权**（通常是 `api/` 主程），其他人提需求 |
| 依赖清单（package.json / build.gradle） | 两人同时加依赖 | 大依赖由一人统一加，赛后各自 `npm i` |
| 全局样式 / 主题文件 | 前端两人同时改 | 拆成 `tokens.css`（定值）和 `components/`（用值） |
| `AGENTS.md` | 谁都觉得该补一句 | 只在固定时间（每 3 小时同步）统一改 |
| 数据库 schema | 后端两人各加一列 | schema 变更走 `docs/architecture/契约冻结.md`，改要记录 |
| `docs/README.md` 索引 | 没人维护就失效 | 每次新增 `docs/` 子目录时同一提交里更新 |
