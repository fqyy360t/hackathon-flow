# 断言清单 (claims)

> 验收的可执行版本。**"验收标准"是给人看的，断言是给脚本跑的。**
> 每条断言只有两种状态：`通过` / `不通过`。不许写"基本通过"。

## 一、必写的四类断言

| 类型 | 断言示例 | 为什么必须有 |
|---|---|---|
| **范围** | 结果全部落在给定范围 / 租户内 | 越界是最容易被追问的 |
| **引用** | 每个引用都真实存在于本轮返回 | 编造 ID 是最致命的 |
| **边界** | 空结果 / 无覆盖 / 错误，三态分明 | 现场必问 |
| **降级** | 外部依赖挂了，不假装成功 | 现场网络必挂 |

## 二、清单

| ID | 断言 | 类型 | 怎么验 | 状态 |
|---|---|---|---|---|
| C01 | <输入固定查询，返回结果全部属于指定范围> | 范围 | 脚本 | 待办 |
| C02 | <引用中的每个 ID 都在本轮返回结果里> | 引用 | 脚本 | 待办 |
| C03 | <空结果返回空列表 + 明确提示，不报错不白屏> | 边界 | 手工触发 | 待办 |
| C04 | <覆盖范围外返回"无覆盖"，不与"零事件"混淆> | 边界 | 手工触发 | 待办 |
| C05 | <依赖不可用时降级，不伪造结果> | 降级 | 断网/关服务 | 待办 |
| C06 | <主链路连续 3 次跑通> | 端到端 | 手工 | 待办 |

## 三、怎么跑

```bash
# 最小做法：一个脚本，全过才打印 PASS
python scripts/check_claims.py
```

脚本要求：
- 每条断言独立，一条失败不影响其他条继续跑
- 输出 `C01 PASS / C02 FAIL: <原因>`，不要只输出总数
- **不许用"同一段代码重复运行"当作通过证明**

## 四、打分口径纪律

如果材料里要放通过率，必须写成：

> 62/74（83.8%）＝ 首轮硬性断言通过率
> 73/74（98.6%）＝ 修复后单轮复测通过率

**不能改写成"问题解决率从 83% 提升到 98%"。** 分母不同、条件不同，一算就穿。

## 五、不许这么写

| ❌ | 为什么不行 |
|---|---|
| 性能提升 80% | 没有基线、没有分母 |
| 测试通过 | 通过什么？几条？跑在什么数据上？ |
| 接口正常 | 正常是指 200 还是指业务正确？ |
| 用户体验良好 | 无法验证 |
