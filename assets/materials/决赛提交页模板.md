# 决赛提交页模板（路演前提交的资料页）

> 用于**进决赛后、路演前**提交的资料页（HTML 详情页 / 表单附件）。
> 它与预赛文档（9 章论证）不是一回事：预赛比"论证严谨"，决赛比"一眼看懂 + 能点开"。
> 结构来自一份真实决赛提交页（某企业首届黑客松 · 充电储能赛道 · 冠军），已按可复用方式重排。

---

## 零、先记住三条

1. **这一页的任务是让评委"点到东西"**，不是让他读完。每个 PART 都要有一个可点的链接或可看的图。
2. **一切事实只定义一次**，其它地方引用同一份。分工、项目名、数字口径最容易三处不一致（见 `交稿前机械检查.md` 第 7 项）。
3. **交稿前必跑一遍机械检查**。这份模板保证结构对，但保证不了链接能打开。

---

## PART 01 基本信息

**评委要什么**：确认你是谁、报的哪个赛道、有问题找谁。

| 字段 | 判据 |
|---|---|
| 项目名称 | 与报名表**逐字一致**，不要缩写或换写法 |
| 参赛赛道 | 用官方的赛道**原名**（官方写"充电储能"就不能写"储能赛道"） |
| 队伍名称 | 与报名一致 |
| 组长姓名 / 联系方式 | 手机 + 邮箱都给；**提交后还要再看一次** |
| 团队成员与分工 | **⚠️ 全文档只在这里定义一次**，PART 05 引用它，不要重写 |

> **分工表的写法**：`姓名（一句话职责）· 姓名（一句话职责）…`
> 每个人只给**一个**身份。如果一个人干了两件事，合并成一句"X 与 Y"，不要在不同章节给不同身份。
> 实测教训：同一份文档里同一个人出现三套身份（基本信息表 / 团队卡片 / 个人介绍标题），评委对照两屏就发现。

## PART 02 项目总览

**评委要什么**：这个问题真不真、你做了什么、凭什么不一样、边界在哪。

### 2.1 项目阐述（三段，一段一句，不要展开）

| 小标题 | 写什么 | 常见错误 |
|---|---|---|
| **解决什么问题** | 谁、在什么处境、缺什么，一句说完 | 写成行业背景综述 |
| **做了什么** | 把哪几个环节连成一条流程，用户看到什么 | 写成功能清单 |
| **亮点是什么** | 用五个动词短语概括原则（如"决策模式封闭、参数结构化、执行前预览、执行后可解释、失败有兜底"） | 写成形容词堆叠（"智能、高效、领先"） |

> **亮点那一行的写法很关键**：用「原则」而不是「能力」。
> ❌ "我们用了大模型 + 动态规划"（是手段）
> ✅ "决策模式封闭、参数结构化、执行前预览"（是约束，体现你想清楚了）

### 2.2 产品逻辑与技术架构

**两段，顺序不能反：先讲一条主流程怎么串起来，再讲分层。**

```
四层：交互层 → 常驻层 → 算法层 → 数据层
一条主流程：用户设定目标 → 常驻层组装快照 → 算法层生成候选与解释
            → 交互层预览确认 → 常驻层受控执行 → 账本核对
```

**每一层要写清"它不做什么"**——这是区分"想清楚了"和"堆名词"的地方：
- 交互层：只读状态、只发提案，不直接写设备指令
- 常驻层：唯一租约 + 看门狗 + STOP 保护，不依赖网页保持打开
- 算法层：在离散网格上联合估值，连续电量线性插值
- 数据层：统一快照与审计，变更留痕
- 数据契约：三方共享，任何一方不自行发明字段

### 2.3 局限性与领先性（**这一节最值得抄**）

> **这是整份文档里最反直觉、也最有效的一节：把局限和领先并列写，局限写在前面。**

**为什么**：评委的工作是排除造假。你先说清边界，他后面看到的每个数字都可信；你只写优势，他会去找漏洞。

**局限性的写法（四条模板）**：

| 类型 | 句式 | 实测例 |
|---|---|---|
| **能力边界** | 不做 ___、不做 ___、不做 ___；首版只维护 ___ | "不做电动车与热泵直接控制、不做售电结算与聚合商合作、不做全屋设备与全品牌电池承诺" |
| **依赖条件** | 需要 ___；___ 不能替代 ___ | "家庭侧需常驻服务与设备数据授权；云端网页不能替代家庭侧常驻连接" |
| **当前完成度** | 当前开放到 ___，其余 ___ 仍在推进 | "当前家庭入口开放到设置保存与规划预览，其余专用计算与真实设备执行仍在推进" |
| **证据边界** | ___ 不能外推为 ___ | "合成设备回放与模拟场次不能外推为德国合同下的真实家庭收益" |

**领先性的写法（每条必须带机制，不带机制的就是口号）**：

| 类型 | 句式 |
|---|---|
| 优化目标 | 以 ___ 评价而非 ___，相对 ___ 基线衡量增量 |
| 适配方式 | ___ 转为 ___ 约束，用量化依据匹配而非按案例套模式 |
| 可解释性 | ___ 放在同一上下文，分列 ___ / ___ / ___ |
| 证据分级 | 区分 ___ / ___ / ___ 三级证据，不互相冒充 |
| **合法的"不做"** | 不必要时如实建议不启用——这是策略的合法输出，不是失败 |

> **最后一条是这份文档最漂亮的一句。** 它把"我们的产品有时会什么都不做"从缺点变成了设计主张。如果你的产品有类似性质，一定要这样写。

## PART 03 成果展示（这一节决定"能不能点开"）

### 3.1 交付物链接

| 项 | 要求 | 检查 |
|---|---|---|
| **在线体验地址** | 公网可达；一条链接直达核心界面 | 手机 4G 点开（见机械检查第 1–2 项） |
| **项目成果报告** | PDF，页数写出来（34 页比"详细报告"可信） | 能直接下载，不需登录 |
| **路演 PPT** | ZIP 或在线链接，写清页数 | 含嵌入视频的说明 |
| **源码仓库** | **真仓库**，README 有"怎么跑 + 验证结果" | 搜全文确认无 `example` |

**每个链接后面加一句"点开能看到什么"**，例如：
> 评委点开即可直接体验（工作台 + 对话助手）

这一句能降低评委的点击成本，也防止他点错。

### 3.2 完整功能演示录屏

- 标"必交"就一定要在，且要在**提交前再点一次**
- 视频地址不要用带 `Expires=` 的签名 URL（会过期）
- 加一句"这段录屏是从哪个入口录的"，让评委能对照着看

### 3.3 产品界面截图（**写法很讲究**）

> **实测写法**：「以下截图取自「软件运行演示」录屏，均为真实产品界面。」

这一句做了三件事：**说明来源、证明不是设计稿、把截图和录屏绑在一起互相印证。**

**每张图的标题只写"看什么"**，不写形容词：

| ✅ | ❌ |
|---|---|
| 家庭总览：实时能流、SoC 与今日累计 | 精美的家庭总览界面 |
| 策略选择：五档策略与适用场景 | 智能策略推荐 |
| 能源账本：累计净费用与原生对照 | 完善的账本功能 |

**数量**：5–7 张，每张对应一个核心功能。超过 10 张评委不会看。

## PART 04 源代码

**最容易被忽略、也最容易出事的一节。**（实测：这一节是一条 404 占位符）

三条硬要求：

1. **仓库公开可访问**（或者提供只读免登录入口）
2. **README 三段**：解决什么 / 怎么跑起来 / 验证结果
3. **敏感信息自查**：密钥、内网地址、真实用户数据、同事姓名手机号

```bash
# 提交前跑一遍
grep -rEi "api[_-]?key|secret|token|password|BEGIN.*PRIVATE KEY" . --include=*.py --include=*.js --include=*.json
git log --oneline | head -20
```

> **如果仓库里有两套本地配置和一堆调试代码，也不要在最后 30 分钟清理**——那条 404 的教训是：**先让链接能打开，再谈仓库整洁。**

## PART 05 团队风采

**评委要什么**：这几个人凭什么能做成这件事（对应评分项"团队能力匹配"）。

### 5.1 团队一句话

写成"能力面 → 架构"的对应关系，而不是"我们四个人很好"：

> 四人覆盖算法优化、后台工程、前端交互与 AI 接入四个能力面，**与「算法只产候选、后台受控执行、前端只读呈现、翻译层封闭集合」的架构一一对应**。

这一句的价值：**证明分工不是凑人数，是照着架构切的。**

### 5.2 成员卡片

**只写三样**：姓名 / 一句话职责（**与 PART 01 完全一致**）/ 一个可验证的资历。

```
熊 ○○ · AI 对话与决策翻译层
用户输入与 API 接入；自然语言到结构化决策对象的翻译；决策对象数据契约
```

**不要在这一格里写业绩数字**——业绩数字放 2.3 领先性，放这里会串。

### 5.3 个人介绍（最容易出错的地方）

**每段固定三段式，且长度相当：**

| 段 | 写什么 | 判据 |
|---|---|---|
| 行业背景 | 与**本项目相关**的经历 | 如果只与本项目无关，删掉或压缩成一句 |
| 本项目负责 | 具体交付物，不是职责名词 | "做了 X 和 Y 两个交付" 优于 "负责 Z 模块" |
| 资质与荣誉 | 最多一行，只留与本项目相关的 | 8 个认证不如 1 个相关认证 |

**三条纪律：**

1. **不要出现别的项目的成绩**（尤其更强的数字）——它会污染本项目的可信度
2. **不要把"跑分 / 评测看板"写成主职责**——翻译成外部语言：`质量度量与回归验证`
3. **四个人的篇幅要接近**——一个人的介绍是别人的三倍，观感上是"这个项目只有一个人在做"

## PART 06 现场纪实

**作用**：证明这是"真的发生过的 24 小时"，也是"团队能力匹配"的间接证据。

- 放**真实照片**：白板、机房、凌晨的屏幕、盒饭、上台前
- 数量 20–40 张足够，做成可点击放大的网格
- 有一段 vlog 更好，但**不要用需要签名/会过期的地址**
- 结尾放传播链接（小红书/公众号）可加分，但**别把传播数据当成果**

> **这一节没有评分项，但它改变了评委对整个文档的信任基调。**
> 一张凌晨四点的白板照片，比十句"我们很努力"有效。
