## 铁律

1. **F 点（提交 − 7h）之后只修不加。** 功能冻结后加功能 = 交付门必挂。
2. **状态只写六种**：`未见实现` / `代码已有` / `局部实测` / `报告待验证` / `完整验收` / `方向待定`。不许写"已完成"。
3. **契约在 `docs/architecture/契约冻结.md`。** 要改先写 `flow/decisions.md`，不许直接改样例。
4. **验收看 `flow/claims.md`，不看感觉。** 断言不通过就不算做完。
5. **未知就是未知。** 🟠⬜ 的假设不进契约、不写死代码，只进 `flow/assumptions.md`。
6. **不许伪造成功。** 依赖挂了要报错或降级，不许用假数据冒充真实结果。
7. **不直推 `main`。** 改代码走 `feat/xxx` `fix/xxx` 分支 → push → 开 PR → 自己合。
   紧急情况（F 点后救火）用 `ALLOW_MAIN_PUSH=1 git push origin main`，并在 `flow/踩坑记录.md` 记一条为什么绕过。
8. **F 点后 `main` 只许一个人推。** 其他人开 PR，由合并权持有人 5 秒内合，**不做 review**（合并的职责是"保住能跑的主分支"，不是审代码）。
9. **PR 标题带范围，末尾带评分项**：`feat(api): 加 /predict [完成度]`。commit message 规范见 `09` §五。

## 开工前必读（顺序）
