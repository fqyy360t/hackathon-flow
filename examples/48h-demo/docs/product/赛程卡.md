## 二、由三个日期推出的四个数

```
D（距提交截止天数） = 11-15 − 10-27 = 19 天
H（比赛时长，小时） = 48h
P（纯准备期天数）   = D − H/24 = 19 − 2 = 17 天   →  M 档（14–24 天）

F 点（系统冻结）    = 提交 − 7h = 11-15 02:00
                      02:00 落在 22:00–06:00 禁改时段
                      → 前移到 11-14 22:00          ← 不是"约等于 7 小时"，是前移
材料冻结            = 提交 − 3.5h = 11-15 05:30
```

**为什么不是"T-19 就是 T-19 排日程"**：19 天里有 2 天是比赛本身，那 2 天不能用来做判断。真正能用来"想清楚"的是 17 天。用 19 排日程，等于把两天的现场时间也算进了准备期，最后一定有一半动作落进比赛里。

**F 点为什么前移**：原值 11-15 02:00 在三更半夜。这个时段人的判断力最差，也最容易出"改一行就好了"的事故。规则是**落在 22:00–06:00 就前移到当天 22:00**——宁可少 4 小时功能，也不要一个凌晨三点的决定。

## 五、这张卡带来的三个决定

1. **不做预赛文档** → 省下的 3 天全部投进 S3 预埋（链路提前跑通）
2. **硬件不能提前拿** → 只能开赛当天拿到，所以**设备相关的代码必须写成"接口可替换"**，用模拟数据先开发
3. **F 点定在 11-14 22:00** → 反推"评分表最晚什么时候到手还能救"：22:00 往前推 8 小时 = 14:00。11-14 14:00 拿到表时正好卡在这个边界上，所以当天只做了 L1/L2 + 一条 L3，没有改架构

> 第 3 条是这个示例里最值钱的一行：**F 点不只是"停止加功能"，它同时是"评分表最晚到达时间"的算法**。
